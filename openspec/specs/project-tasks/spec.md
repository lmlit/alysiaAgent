# project-tasks — 委托任务（聊天侧把工程活交给 dsh 执行）

> 建立于 2026-10-17（change: `add-project-task-delegation`）。
> 上游计划：`docs/ALYSIA-DSH-BRIDGE-PLAN.md` 阶段 C/D；
> 前置：`dsh-adapter` §2.7（服务器侧运行体）、§2.5.2（委托会话不进记忆）。

## 1. 定位与边界

**她要能把工程活交出去、看到结果、再提修改意见 —— 而且不丢任务、不污染记忆、不越过权限。**

| 部分 | 负责 | 不负责 |
|---|---|---|
| 聊天侧（她） | 提目标、选项目、提修改意见、**验收** | 不直接跑工程命令 |
| 任务层（本 spec） | 持久化、去重、单并发、状态机、结果通道 | **不做 Agent 推理** |
| 宿主 runner | 认领任务、跑 `dsh`、回传结果 | 不做业务判断（不写 `completed`） |
| dsh 运行体 | 用工程工具干活、保留工程会话 | 不动画像、不碰其他项目 |

### ★ 决定架构的既成事实

alysia server 跑在**容器里**，`dsh` 与博客工作区在**宿主机上**
⇒ 服务端**无法** spawn dsh。故走**宿主侧 runner 主动轮询认领**（出站连接）：
不动容器、不动镜像、工作区天然在宿主上。

**否决**：① 把 dsh 装进镜像（要背整个 Node 运行时，且工作区挂载面扩大）；
② 服务端 `docker exec` 到宿主（方向反了，且要挂 `docker.sock` = 给容器 root）。

## 2. 数据契约（`project_tasks` 表）

| 字段 | 语义 |
|---|---|
| `task_id` | `pt-<uuid>` |
| `request_key` | **UNIQUE**，同一次调用的重试去重 |
| `project_id` | 必须在 `config.yml` 的 `projects:` 里登记过 |
| `origin_session_id` | 发起任务的聊天会话（结果要能回到那里） |
| `origin` | `user`（用户显式下令）/ `delegated`（她在对话里决定交出去） |
| `goal` / `acceptance_criteria` | 目标与验收标准，**原样**给执行端看 |
| `dsh_session_id` | 经真实响应确认的工程会话 id；`NULL` = 还没有 |
| `status` / `revision` | 状态与轮次（`revision` 从 0 起，每提一次意见 +1） |
| `result` / `artifacts` | 结果摘要、**受限**产物引用（只存工作区相对路径） |
| `attempts` / `last_error` | 认领次数与失败原因（自愈与排障依据） |

**契约 1（去重）**：同一 `request_key` 再次提交 ⇒ 返回**既有任务**（`deduped`），不新建。
**契约 2（单并发）**：同一项目同时最多**一个**在途（`queued`/`running`）任务；
第二次提交返回 `busy` + **既有任务**（不丢弃、不新建）。
**契约 3（顺序）**：先去重、**再**判忙 —— 顺序写反会让「同一次调用的重试」被误报成「新提交被拒」。
**契约 4（路径）**：`workspace`/`profile` **只能**来自服务端配置，模型与工具都不能提供。

## 3. 状态机

```text
queued ──认领──▶ running ──回传──▶ needs_review ──接受──▶ completed
                    │                  │
                    ├──▶ failed        └──提意见──▶ revision+1 ──▶ queued
                    └──▶ unknown
```

| 状态 | 含义 |
|---|---|
| `queued` | 待执行（含「续作」——revision 已 +1） |
| `running` | 已被 runner 认领 |
| `needs_review` | 这一轮跑完了，**等验收** |
| `completed` | 本轮结果**被接受**（⚠️ **不等于已发布**） |
| `failed` | 有明确失败证据（不是网络超时） |
| `unknown` | **无法确认**是否执行成功 ⇒ **绝不自动重投** |

**契约 5（runner 不写 `completed`）**：执行方只能写 `needs_review`/`failed`/`unknown`。
「跑完了」与「验收通过」是两件事，混起来会变成自证。
**契约 6（迟到回传）**：只接受仍在 `running` 的任务回传；其余一律拒绝（不许覆盖新一轮）。
**契约 7（自愈）**：`running` 超过 `claimedTimeoutMs` 视为认领方丢失，可被重新认领；
`attempts` 用尽 ⇒ `failed` + 明确原因（**响亮失败，不静默饿死**）。
**契约 8（续作沿用会话）**：提意见 ⇒ `revision+1`、回 `queued`，**`dsh_session_id` 不变**
（否则第二轮等于重新建站）；在途状态**不接受**意见。

## 4. 接口

见 `docs/Web-API-Design.md` §2.4.5（五个端点）。要点：

- `POST /api/project-tasks` / `GET …/:id` / `POST …/:id/revision` —— **聊天工具**用
- `GET …/next` / `POST …/:id/result` —— **runner** 用
- 认领响应里**带项目配置**（`workspace`/`profile`）⇒ runner 不读第二份配置（单一来源）
- 与既有端点**同一套 Bearer 鉴权**，不新开通道

## 5. 宿主侧 runner（`scripts/project-task-runner.mjs`）

**契约 9（`--session-id` 只在已有会话时带）**：首轮带了会报 `unknown id`；
续作不带就等于重新建站。

**契约 10（终态映射）**：`turn_end.reason.kind === 'completed'` ⇒ `needs_review`；
`'error'` ⇒ `failed`；取不到/超时 ⇒ `unknown`（**不自动重投**）。

**契约 11（回传失败不假装成功）**：runner 回传失败只留痕，任务停在 `running`，
由服务端的**认领超时**回收 —— 不许把「没回传成功」写成任何终态。

**契约 12（零副作用可验收）**：任务正文只给目标与验收标准；执行端**不得**被要求改工作区以外的东西。

## 6. 记忆与权限

**契约 13（委托会话不进记忆）**：委托运行体的每条回传带 `payload.dsh_origin`
（见 `dsh-adapter` §2.5.2）⇒ 服务端打 `skip_profile` + `synthetic`，**且不结算**。
**契约 14（产物受限）**：`artifacts` 只存**工作区相对路径**与摘要；
服务端**不读**宿主文件系统（它在容器里，看不到那些路径）。
**契约 15（无取消）**：首版**不提供** cancel —— dsh 协议层没有取消（只能杀进程），
「本地不再等待」不等于「远端已停止」，那种假照不能进工具。

### 6.1 执行体的运行身份（2026-10-18，change: `harden-delegated-runtime`）

**为什么先做这个、而不是先做审批**：「删库删表 / 暴露网关」这类动作，最可靠的处置**不是问她，
而是根本做不到**。审批层只该处理「合理但需点头」的动作；能力边界让「不该做」的进不了门。
（三层强度：**能力边界 > 审批 > 指令黑名单**。黑名单永远漏——`mv`/`dd`/`>`/`chmod`/`docker`/`systemctl`
都能删东西；而且判据若来自模型自述，等于没有闸。）

**契约 18（非 root）**：委托运行体以专用用户 `alysia-runner` 运行，**不得**以 root 跑。
服务端进程是 root，但它**不执行**；执行方是宿主上的 `alysia-task-runner.service`。

**契约 19（独立 `DSH_HOME`）**：`/srv/alysia-runner/.dsh`，与 root 的 `/root/.dsh` 完全隔离。
理由：后者含 `.credentials.yaml` 与**全部 dsh 会话历史**（她与用户的对话），共享等于把它们交出去。

**契约 20（读边界，实测 8/8 拒绝）**：`alysia-runner` 必须**读不到**
`/root`、`/root/alysia`、`/root/alysia/data`、`alysia.db`、`.env`、`/root/.dsh`、`.credentials.yaml`。
落实方式是**两道屏障**：`/root` 750 + `/root/alysia/data` 750、`/root/alysia/.env` 700
（⚠️ 改的是 other 位，**不动 owner/group** —— `data` 属主是容器内用户，动了就断她的记忆写入）。

**契约 21（工作区在 `/srv`）**：工作区 `= /srv/alysia-runner/blog`。**不得**放在 `/root` 下——
`/root` 是 750，非 root 连穿越都不行。

**契约 22（凭据经 `EnvironmentFile`）**：`/etc/alysia-runner.env`（`600 root:root`）；
systemd 以 root 读该文件再降权 ⇒ 进程里有 token、**runner 用户自己读不到**。
⚠️ 有意保留的取舍：进程仍持有**全权** token（否则回传不了）——
「只许调 ingest / project-result 的受限令牌」是后续项。

**契约 23（常驻）**：`alysia-task-runner.service`（`User=alysia-runner`、`Restart=always`、
日志 append 落盘）。**契约**：轮询失败（含服务端 5xx）**不得**让 runner 退出——
实测容器重建期间收到 `HTTP 500`，它按间隔重试并在容器就绪后正常认领。


## 7. 能力开关

**契约 16**：`config.yml` 的 `projects:` 为空/缺省 ⇒ **三个工具都不注册**（配置即开关）。
**契约 17**：`loadConfig()` 是**逐字段挑选**的 —— 新增配置段必须同时改映射，
否则就是「配置写了但没人看见」（本项真机第一次跑就撞上：容器里 `config.yml` 有 `projects:`，
服务端却报「已登记：无」）。坏条目**留痕**，不静默丢。

## 8. 已知限制

- **模型是否真按要求做，本层不保证**：真机第二轮 `final` 仍是旧码（未定位，见
  `archive/2026-10-17-add-project-task-delegation/e2e-evidence.md` §3）—— 属**验收**问题。
- **`request_key` 用的是「会话 + 项目 + 目标正文」**，不是真正的调用 id（pipeline 目前不给）。
  够用是因为真正的并发保护是「同项目单在途」；同一轮网络重试正文相同 ⇒ 会被 deduped。
- 首版只有**一个**登记项目、**单**项目串行；无并行调度、无定时/自主发起、无发布。
- **出站网络未收窄**（博客构建要拉 npm / 字体）：她仍可出网，只是读不到凭据与记忆库。
  「出站白名单」列为后续。
- **没有人在环上的逐次审批**（`add-approval-gate`，pending）：需要人工点头的动作目前
  要么被沙箱直接拒，要么就是放行 —— 中间没有"问她"这一档。
- **未在运行中抓到 dsh 子进程的 uid**：只证明了父进程是 `alysia-runner`（非 root）。

## 10. 结果回送（2026-10-18，change: `return-project-task-result`）

**为什么有这一节**：用户问「编程出结果了，她会告诉我吗？」—— 当时的答案是**不会**。
`dsh → runner → POST /result → 写进任务表`，**这条线上没有她**；而委托会话又被整段排除在记忆外
⇒ 表现为「我交出去了」（说的）→ 然后失忆。

**契约 24（回执落回原会话）**：任务进入终态时，向 `originSessionId` 写一条**类型化事件**：
`id = project-task:<taskId>:r<revision>`、`source='system'`、`role='assistant'`、`perspective='self'`。
- **幂等**：同一条结果重复回传命中既有 id；不同轮次不同 id。
- **防污染**：`skip_profile` + `synthetic='project-task-result'` + `project_task_result=true`
  ⇒ 进 `getRecentMessages`（她下一轮能回忆），但**不进**画像/人格/嵌入/摘要。
- **不猜目标**：`originSessionId` 为空 ⇒ 不写（宁可不记）。

**契约 25（通知失败不许改任务状态）**：`notifyProjectTaskResult` **不 await**，
记回与推送各自 try/catch；最差是"没通知"，不是"任务被判失败"。回传被拒（409）时**不触发**回送。

**契约 26（结果必须带地址）**：「做完了」对用户不够用 —— 用户真正会问的是**"给我链接"**
（真机上确实问过，而她答"我没存下能直接点开的地址"）。
⇒ 回执正文末尾必须带 `projects.<id>.publicUrl`（配置项，**不由模型提供**）。

**契约 27（通知只发一条）**：QQ 实现对「>60 字或含换行」的文本会**自动分段**（≤3 段、段间停顿）
—— 那对"她说话"是设计，对**通知**是噪声（一条事变三条消息）。
⇒ 工具类通知必须传 `maxSegments: 1`。

**契约 28（只在能确定目标时推）**：`originSessionId` 形如 `qq-official-1:private:private_<openid>`
才推（**先按冒号切最后一段再剥前缀** —— 对整串用正则最左匹配会取到 `private_<openid>`，
QQ 返回 `11255 请求的资源不存在`，这个坑已经踩过）；`webui:` / 测试会话跳过并留痕。

**已知边界**：回执**不进摘要** ⇒ v1 只保证**近期窗口**可回忆，不是长期记忆。

### 10.1 她的口吻（2026-10-18 追加，同 change）

**为什么有这一节**：用户看过头一版回执后说「返回的东西要过一遍提示词不，**感觉好干啊，
而且没有昔涟的味道**」。这个批评指向的是**契约问题**而不是文案问题：

> 那条回执是 `role: 'assistant'` —— 它以**她说过的话**的身份进她的对话史。
> 模板腔放进去，等于让她的记忆里留着一句她绝不会说的话。

**契约 29（用她自己的措辞）**：回执正文必须由 `composeProjectTaskNotice()` 生成
（人格名 + 事实 → 一句她的话），**不是**模板拼接。模型失败才回落模板，
且回落时正文带「（委托任务回执）」字样 —— **回落必须可辨认**，不许假装是她的语气。

**契约 30（提示词的边界）**：只给**事实**（状态/产物/地址/执行端最后一句），
**不给**"该怎么夸自己"；明确禁止：编造完成情况、替用户验收、提内部概念
（"委托任务/任务表/状态机"）、**描述通知机制本身**（真机出现过"工程那边说通知已经发出来了"）。

**契约 31（地址逐字，且只出现一次）**：
- 模型改写 URL 是常见事故 ⇒ `finalizeNotice` **兜底校验**，缺了就以代码为准追加，不跟模型商量；
- 但她的话里**已经带地址**时不再追加"外网地址："那一行 —— 真机上出现过同一句里地址出现两遍。

**契约 32（采样必须有 `max_tokens`）**：这条 LLM 调用显式带 `max_tokens`。
理由是本仓已经炸过三次的 KI-1：**没有上限的槽**（会话摘要 22 天 / 每日反思 11 次 / 画像提取 6 个月）。

**已知小瑕疵（记在案）**：回执末尾仍会附上执行端最后一段话（真机样本是 `NOTIFY-OK` 这类测试串）。
真实任务里那段通常是有用的交代，所以暂时保留；若觉得吵，下一个 change 再做"摘要压缩"。

## 11. 基站（展示层总入口，2026-10-18，change: `add-preview-hub`）

**为什么有这一节**：用户原话——
「现在她做的东西给我们展示只有通过一个链接，只能展示一个东西，我们是不是可以搞个**基站**，
里面嵌套她做的网页呢」。
在此之前是"一个项目一个地址"，每加一个项目就得有人给她一个新链接，**没有"她做过的事都在哪"这个地方**。

**契约 33（一个总入口）**：`/` = 基站，列出**所有**已发布的项目；每个项目在自己的子路径 `/p/<项目>/`。
两层地址都必须在 `AGENTS.md` 与 `.alysia-project.json` 里给她 —— 她要能自己说出"在基站上"。

**契约 34（生成，不手写）**：基站首页由生成器产出（`scripts/preview-hub.py`，root + systemd timer 每 10s）。
判据：`<workspace>/public/index.html` 存在 ⇒ 已发布。**"自动"必须包括移除**：
不再登记/未发布的项目，其卡片与链接都要消失（手写首页一定会腐烂：新的忘加、删的没删）。

**契约 35（幂等 + 原子）**：链接目标已经对就不重建；`index.html` 先写 `.tmp` 再 `os.replace`
（否则浏览器会读到半个页面）。timer 每 10s 跑一次，所以这两条是**硬要求**，不是优化。

**契约 36（用子路径，不用 iframe）**：`/p/<id>` 是指向各项目 `public/` 的**符号链接**（root 建）。
iframe 在滚动/深链/移动端都别扭，还要和 `X-Frame-Options` 打架；子路径才是真正的嵌套。

**契约 37（边界不破）**：她仍只能写自己工作区的 `public/`；**碰不到基站**（生成器与链接都是 root 的）。
基站样式 v1 不归她（统一卡片墙）—— 这是刻意的：展示层要稳，才能可靠地反映"她做了什么"。

**契约 38（`publicUrl` 指具体页面）**：`projects.<id>.publicUrl = <base>/p/<id>/`。
回执与推送带的是**她刚做的那个页面**，不是基站根 —— 用户问"给我链接"时要一步到位。

**契约 38b（她的文档要交代基站目录，且讲清"能读不能写"）**（2026-10-18，change: `document-hub-dir-to-author`）：
工作区的 `AGENTS.md` 必须写明基站目录（`/srv/alysia-preview`；`p/<项目>` 是指向 `public/` 的符号链接）、
生成器位置、**每 10 秒重建**、以及「你能读不能写」。
理由：`/srv/alysia-preview` 是 `755` ⇒ **她本来就能读**，"藏着不说"不成立；
而写操作全被拒 ⇒ 说清「不能做 + 为什么 + 该怎么做」比让她白试一轮更省事。
⚠️ **写权限仍然不给**（契约 37）：展示层要稳。她想要自己的门面，正确形态是**受限写口**（如只给 `hub.css`）。

## 12. 认领模型：一个 runner 服务所有项目（2026-10-18，change: `claim-across-projects`）

**为什么改**：为了验证基站会长卡片，登记了第二个项目 `alysia-toys` 并提交任务 ——
**任务停在 `queued`，580 秒没人认领**。原因：runner 是按项目起服务的
（`--project alysia-blog` 写死）⇒ 每加一个项目就得再加一个服务，**漏了就静默排队**。
这比"要多起一个服务"更糟：**它是静默的**。

**契约 39（一个 runner 服务所有登记项目）**：`GET /api/project-tasks/next` 的 `projectId` **可选**。
不带 ⇒ 由服务端决定；带 ⇒ 只认领该项目（隔离/调试用），未知则 400 并**列出已登记**。

**契约 40（取最老的活，不饿死后登记者）**：不带 `projectId` 时先 `nextQueuedProject()`
（`SELECT project_id ... WHERE status='queued' ORDER BY created_at ASC LIMIT 1`），
再 `claimNext(那个项目)`。
★ **认领本身仍原子**：这一步只**读**不改状态，真正的"找最老 → 标 running"仍在
`claimNext` 的**单事务**里 ⇒ 两个 runner 并发也不会双认领（契约 5 未被削弱）。

**契约 41（注销的项目不许静默丢活）**：排队任务所属项目已从登记表移除 ⇒ **不执行**、
**留痕 warn**、返回空 —— 不许"看起来在跑"。

**契约 42（失败要响亮）**：runner 的 `--project` 由必填改为可选时，必须同时改掉
代码里的硬校验（`if (!cfg.project) exit(2)`），不能只改 usage 文案。
⚠️ 我第一次就漏了这条，结果服务 `activating`、日志刷满帮助文本 —— 记在案。

## 13. 验收能力：她能"看"自己的页面（2026-10-18，change: `give-author-eyes`）

**动机**：她做完页面只能 `grep` 出「零外链」、`curl` 出 200 ——
**布局塌了、字被裁了、主题错了，自检照样全绿**。`needs_review` 一直是空壳。

### ★ 13.1 前提被实验推翻：她本来就能看图

立项假设是「她是文本模型，看不见样式」。**实测推翻**：给她一张**没写过、无从推断**的图
（随机 6 位码 + 两个彩色圆点，无同名文本），她准确读出 `CJZJYJ` 与两个圆点的位置/颜色；
同一轮还**拒绝编造**视觉描述（"现编一段就是骗你了"）。

⇒ 这个 change 的形态从"给她眼睛"改成"**给她一台相机**"：`shot.sh` 只负责
把页面变成**一张她能打开的图**；把图讲成话的那条（GLM-4V）降级为**旁路**。

**契约 43（文档不许写"你看不见"）**：工作区文档里**不得**声称她看不见图。
理由：错的文档会**塑造错的行为** —— 她会表现得像个瞎子，明明能看却只用 grep 糊弄。
文档应写：**你能看图**（附实测证据）+ `shot.sh` 是相机 + 去哪看产物。

### 13.2 两个"自检全绿但页面是坏的"的渲染坑（必须写进她的文档）

| 坑 | 现象 | 根因 |
|---|---|---|
| 无中文字体 | 中文全 `□□□` | 服务器 `fc-list :lang=zh` = 0（装 Noto Sans CJK 后 31） |
| 深色主题丢失 | 深紫页拍成**白底** | 页面用 `@media (prefers-color-scheme: dark)`，而 headless **默认浅色** |

⇒ **契约 44**：截图默认按**深色**（`preferredColorScheme=0`，实测左上角亮度 247→30），`--light` 可切。
理由：同一页在真实浏览器与默认截图里是**两个样子**，拿错那张验收会得出**完全相反的结论**。

**契约 45（旁路不是判据）**：`--vision`（GLM-4V 描述）默认**关**：
① 她的 bash 环境里拿不到 `ALYSIA_WEBUI_TOKEN`（dsh 对工具环境脱敏 —— 这是**好事**，别绕）；
② **她自己看比它准**：实测同一页 GLM-4V 说「白色为主色调」（实际深紫），她说的全对。
文档必须写清：**它说得笼统或不对，信你自己。**

### 13.3 服务端契约

**契约 46**：`POST /api/vision/describe`（Bearer 鉴权）：
`{ imageBase64, prompt? }` → base64 解码 → **容器内临时文件** → `VisionBridge.describe(path)` → 删（**成败都删**）。
语义必须明确：**无视觉模型 501** / 缺图 400 / >8MB 413 / 模型没返回 **502**（不许 200+空串）。
**不传 URL 而传 base64 的理由**：服务端在容器里拿不到宿主路径，也不该多一条"容器能不能访问宿主端口"的隐形依赖。

**已知边界**：交互态（hover/点击后）不拍；无像素级回归比对；**服务器没有中文衬线字体**（`serif` 会退回黑体）。

## 14. 执行窗口：只在 DeepSeek 空闲时段跑（2026-10-18，change: `gate-project-tasks-to-offpeak`）

**用户规则（北京时间）**：**高峰** = 周一至周五（**不含**中国法定节假日）9:00–12:00、14:00–18:00；
**空闲** = 其余全部，含周末与法定节假日全天。

**契约 47（高峰只排队，不执行）**：`GET /api/project-tasks/next` 在高峰返回
`{ok:true, task:null, paused:{reason,until,message}}` —— 这是**正常状态**（不是错误），
且**不许**调用 `claimNextProjectTask`。
理由：钱按执行时间算，排队不花；而"拒收任务"等于让用户和模型都去记时段。

**契约 48（不拒收，但要说明白）**：`start_project_task` 在高峰**照样收**，回执必须带
「现在是高峰时段 … 要等到 HH:MM 之后（北京时间）才会开始跑 —— **到点自己会跑，不用再交一次**」。
那句"不用再交一次"是给模型的行为约束：否则她会重复提交。

**契约 49（时区自己算，UTC+8）**：判定**不得**依赖宿主时区（容器常是 UTC）。
必须显式用 UTC+8 换算 —— 错 8 小时会把"高峰"搬到凌晨，是最坏的一种"看起来生效了"。

**契约 50（节假日表不内置）**：法定节假日由 `projectTasks.holidays` 提供（`YYYY-MM-DD`）。
**未列出的日期按工作日处理** ⇒ 窗口照常生效 ⇒ 只会更省，不会多花。
理由：节假日每年公布且涉及调休，**猜一份错的表比没有更糟**。

**契约 51（"为什么不动"要有答案）**：`GET /api/project-tasks/window` 返回
`{window:{offPeak,reason,nowBeijing,until,message}, config:{peakWindows,holidays,nowOverride}}`。
加闸门后第一个问题一定是这个 —— 端点就是那个答案。

**契约 52（排障时钟必须响亮）**：`projectTasks.nowOverride`（ISO）可固定判定时刻，
但**配了就打 WARN**（`⚠️ … 排障用，生产请删掉这一项`）。理由：高峰分支只有工作日
9-12/14-18 才触发，不在生产上验一次就等于没验过。

**契约 53（暂停日志不许刷屏）**：runner 在 `paused` 时只在**说法变化**时打一行日志。
理由：15 秒一条同样的"暂停"会把真正的问题淹没。

## 15. 归属：回执不是她的话（2026-10-18，change: `attribute-engine-receipts`）

**用户原话**：「我们工程的回执是不是要上下文带上，不如让自己调工程的回复，
**她以为是我命令输出的**」。

**为什么这是 bug 而不是文案问题**：旧实现把回执写成 `payload.role = 'assistant'`，
而三处渲染器全是「**不是 user 就当成她**」⇒ prompt 里出现：

```
[23:41] 昔涟: （委托任务回执）项目 alysia-blog 第 1 轮已结束：needs_review。
```

**等于替她写了一段她没说过的话。** 后果两个方向都坏：她以为自己讲过；或把那句机器口吻
当成"用户命令的输出"，从而误判自己做过什么。

**契约 54（第三种说话人）**：记忆事件的 `role` 取值必须能区分 **用户 / 她 / 执行端**。
执行端用 **`engine`**，渲染标签是「**工程端**」（不是「昔涟」，也不是「你」）。

**契约 55（共享渲染函数）**：**所有**把事件渲染成对话行的代码必须调用
`dialogueSpeaker(role, labels?)`（`core/src/memory/render-dialogue.ts`），
**禁止**再各自写 `role === 'user' ? … : …`。
理由：三处独立实现正是这个 bug 的成因；同一个错误被复制三遍，改一处漏两处。

**契约 56（未知 role 仍当作她）**：历史数据只有 `user`/`assistant`；新增角色时
**不得**让老数据被渲染成"工程端"或"用户"。兼容规则由该函数单测钉住。

**契约 57（正文自带来源）**：回执正文首行必须是 `【工程回执·来自 dsh 执行端】…`。
**双保险**：即便某个未来渲染器把角色认错，文字本身也标明了来源。

**契约 58（口吻与归属分离）**：**记忆回执**用事实 + `engine` 归属；
**QQ 推送**才用她的口吻（那时真的是她在对用户说话）。
⇒ **取代 §10.1 中"回执用她自己的措辞"的做法**：那个决定建立在"这条是她说的"这个
错误前提上；前提没了，做法就要收回。

## 16. 她自己发起（2026-10-18，change: `let-her-start-her-own-projects`）

**用户原话**：「让她的生活/主动事件系统也能发起"做网站"（比如她自己在 idle 时决定做个小页面）」。

**这个功能的难点不是"能不能"，是边界**：她能自己发起 ⇒ 同时发生**花真钱**、
**在她工作区写文件**、**可能改变对外可见的东西**。所以每条规则都在挡这三种风险。

**契约 59（六道护栏，按顺序判）**：开关 → **空闲时段** → **无在途任务** → **今日未达上限**
→ **距上次自发起足够久** → **用户已安静足够久**。
任一不过就不做，并把原因大写进日志（`⏭ reason：detail`）。
为什么"用户刚说过话就不做"：用户在的时候她该陪用户，不是跑去干活。

**契约 60（她自己说想做什么）**：任务目标由 `composeSelfActivityIdea()` 生成
（人格 + 能做/不能做的清单），**不给审美要求**。
⚠️ 该调用**必须给足 `max_tokens`**：实测 200 时返回空串（reasoning 吃光预算 = KI-1）。
空串 ⇒ **这次放弃**，不许拿模板硬凑成"她想做"。

**契约 61（必须显式 projectId，留空不发）**：
真机事故：先前"留空 = 用登记列表最后一个"⇒ 她落到 `alysia-blog`（精心做的正式页面），
一个验证触发的任务去改正式页面的风险**不该存在**。
⇒ 现在留空**不发**并在启动时警告。**猜项目 = 猜她往哪个工作区写文件，不许猜。**

**契约 62（默认不发布）**：`allowPublish` 默认 `false`；验收标准里写死
「**不要发布**（不要跑 publish.sh）—— 做好留在工作区，等对话里再决定要不要放上去」。
理由同 §11 契约 37：展示层要稳，才能可靠地反映她做了什么。

**契约 63（`origin: 'self'`）**：与 `user` / `delegated` 区分；store 读回的同形判断要一起改
（否则读回来会变成 `user`）。

**契约 64（模块必须声明 provides）**：`al:self-activity` 调 `ctx.provide(...)` ⇒
**必须** `provides: ['al:self-activity']`。
⚠️ 真机事故：写成 `provides: false` ⇒ kernel 拒绝 ⇒ **apply 失败 ⇒ 整个 Alysia 起不来 ⇒ 容器重启 7 次**。
那不是"这个模块挂了"，是**全站挂掉**。

### 16.1 预览服务：必须多线程（同 change 交付的相邻修复）

**契约 65**：静态预览服务必须**并发安全**。
根因：服务器 python 是 **3.6**，`http.server` 在 3.6 仍是**单线程**。用户浏览器、她自己截图、
基站三者同时取页面时就会排队，实测 `Recv-Q 6` 与**间歇性 `000`**。
⇒ 用 `scripts/preview-serve.py`（`ThreadingMixIn`）。

**契约 66**：越界防护只做**词法**校验（`abspath`），**不得**用 `realpath` ——
`p/<项目>` 本来就是指向各工作区的**符号链接**，`realpath` 会把它们误判成越狱，
使页面**静默回落成基站首页**（实测 16224B → 2455B）。目录列表一律 404。

## 17. 「做一件东西」是状态机，不是一次性任务（2026-10-18，change: `make-author-iterate`）

**动机（用户三连）**：「生成的东西 ai 味道好重啊」→「她调用工具生成的东西，没有她自己的味道」→
「**她和工具应该要有交互才行啊**」。

诊断：她每次都在白纸上**一次成型**（写完 → grep → curl → 交），中间没有"看一眼、不满意、再改"。
**味道长在来回里，不在第一版里。**

**契约 67（阶段化）**：一个"做东西"的任务必须分阶段推进：
`intent → sketch → review → build → revise → statement → publish → done`。
**每个阶段是一次独立的执行端运行**（不是让模型自己在一轮里自觉走完）。
阶段指令由**服务端**下发（`PHASE_PROMPTS`），runner 不在本地抄一份（单一来源）。

**契约 68（判据取文件事实，不取自述）**：能否进下一阶段**只**由从工作区读出的事实决定：
`NOTES.md` 的四个标记（`## 意图` / `## 自评` / `## 选的` / `## 哪里像我`）、
`drafts/*.html` 数量、`shots/draft-<名>.png` 是否存在、`shots/revise-N.png` 是否存在、
根目录是否有做出来的页面、`public/` 里是否有同名页面。
⚠️ **不许**采信"我改好了"这类自述 —— 本项目已栽过同类（回执自述 ≠ 真做完）。

**契约 69（硬下限：≥2 张草图 + ≥1 轮改动）**：
草图 < 2 或有一张没拍 ⇒ 停在 `sketch`；没有 `revise-N.png` ⇒ 停在 `revise`；
`## 哪里像我` 没写 ⇒ 停在 `statement`。**"一版就满意"不算完成。**

**契约 70（轮次上限 = recursion_limit）**：`maxRounds` 默认 8，超了收工成
`needs_review`（交给人），**不许无限重试**。

**契约 71（状态累积且不可变）**：`loop_state` 记 `rounds`/`visits`/`revisions`；
推进返回**新对象**（不改入参）。`visits` 能看出她卡在哪个阶段。

**契约 72（能不能上线只由配置决定）**：走到 `publish` 阶段是否真发布，由
`projectTasks.allowPublish`（默认 `false`）决定。**执行端不能自己决定上线。**

**真机证据（2026-10-18）**：一轮任务跑了 6 个阶段，每阶段一次 dsh 运行：

```
intent    → sketch    · 意图已写（242 字）
sketch    → review    · 3 个草图都有截图
review    → build     · 已选 a，自评 1331 字
build     → revise    · 完整版已就位：waiting.html
revise    → statement · 已拍过一轮并改过（revisions=1）
statement → done（ready）
```

她的 `NOTES.md` 自己写下了这套流程的价值：
「最不像我的：**b**……这套语汇和『慢时钟』几乎是同一套。意图里明明写了『这次不用夜色帮忙』，
**b 一上手又把夜色请回来了，这是我这一轮最该认的错**」；
重做那轮她又抓到自己在**完整版里重复了刚批评过的错误**（页脚以下 40% 是空），并改掉了。

**已知不足**：① 阶段边界靠**指令**约束，她可能"顺手多做"（实测 `statement` 轮多做了一页
`lift.html`）；② 成本约 6 倍；③ `publish` 阶段尚未真机验证（配置未开）。

### 17.1 阶段外写入：硬拦 + 不销毁（2026-10-18 补丁）

**契约 73（阶段写入白名单）**：每个阶段只许写这些路径：
`intent`/`review`/`statement` → 仅 `NOTES.md`；`sketch` → `drafts/*.html` + `shots/draft-*.png`；
`build`/`revise` → 根目录页面文件 + `shots/revise-N.png` + `NOTES.md`；`publish` → `public/**`。

**契约 74（快照 + 回滚，且**不销毁**）**：阶段开始前记账（路径 → `size:mtime`），
结束后比对；越界的**新增/修改**一律**移出**工作区到 `.phases/violations/r<N>/`（**不删**），
删除也记一笔；越界条目写进回执（`[阶段外写入已移出] …`），让她知道"这轮多做的被移走了"。
理由：回滚是"我们改了她的东西"，必须让她看见，否则她会以为自己写丢了。

**契约 75（通知必须有"她怎么说话"的上下文）**：任务通知的措辞生成**不得**只喂
"事实 + 人格名"——那是**通用人格**。必须与聊天回复同源：注入**最近对话**（24h 窗口）。
⚠️ 真机对比：同一个页面，旧通知（无上下文）与她的实际语气明显不同人。

**契约 76（「哪里像我」随通知一并送达）**：她 `NOTES.md` 里的 `## 哪里像我` 原文
（截断 260 字）要附在推送末尾（`她自己的话：…`）。
理由：那是她最有辨识度的文字，原先只被阶段闸门读、**人看不到**；
附**原文**而不经模型改写，保证她的话原样到用户手上。
