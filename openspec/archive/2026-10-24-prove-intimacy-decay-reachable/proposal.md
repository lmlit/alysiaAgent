## 动机

亲密度「无互动衰减」在**默认旋钮下永远不触发** —— 用户一年不说话，亲密度一动不动。

**这不是"没修过"，而是"修的时候弄坏的"**：

| 时点 | 改动 | 可达性 |
|---|---|---|
| `7f08f73`（初版） | 窗口 `since7d` = 7 天；条件 `idleDays >= 3` | ✅ 可达 |
| **`07c9016`（2026-08-07）** | 修「旋钮从未参与决策」：硬编码 → `decayThreshold = 2 + round((1-0.4)×10)` = **8** | ❌ **不可达** |

窗口没动过 ⇒ `idleDays` 可观测上限 = **7**，且兜底写死 `: 7`；阈值 **8**。**8 > 7，条件恒假。**

生产库实测（`.video-demo/data/alysia.db`，非默认值推测）：

```
memory_config = {"decay_rate":0.3,"importance_threshold":0.4,...}
→ decayThreshold = 8 天, 每日衰减 = 1.8
→ 可见窗口 7 天, 兜底 idleDays = 7   ⇒ 不可达
```

**关键：光调阈值无效。** 即使把阈值降到 7，衰减幅度 = `1.8 × (7−7+1)` = **1.8**，
只衰减一天量就封顶。**窗口不解决，阈值调多低都只衰减一次。**

## 需求（做什么）

- [ ] **P2 · 判据与窗口解耦**：`updateIntimacy()` 的 `idleDays` 改用
      `memoryManager.getLastUserMessageAt()`（全表 SQL，无窗口），不再在
      `getRecentMessages(sid, 500, now−7d)` 里反查 `role==='user'`
- [ ] **P2 · 干掉哨兵值**：`idleDays = lastUserAt ? … : 7` 里的 `7` 改为 `null`
      （语义 = 「从未说过话」），由调用方显式处理：**不衰减 + 一次限频 debug**，
      不再用「7」冒充真实天数
- [ ] **P3 · 判据收成一份**：与推送闸那条 idle（`idleDaysSinceUserMessage()`，
      已正确用 `getLastUserMessageAt`）**同源**；本 change 内先做到"同函数同判据"，
      真正的结构收敛（`context-facts.ts`）留给 P8 第 1 步
- [ ] **★ 可达性用例（本 change 的核心）**：构造 **≥8 天** 的 idle，断言**衰减真的发生**；
      并至少有 7 天（未过阈值）/ 8 天（刚好跨过）/ 30 天（远超）三个点
- [ ] spec `ai-life-system` §11 补「可达性契约」：阈值判据必须给出跨阈值两侧的用例

## 设计决策

**不动任何系数。** 阈值 8 天、衰减 1.8/天、四档边界 24/40/70 —— 全部保留。

理由：没有运行数据。`docs/TODO.md` 里同类条目（`tune-recall-with-runtime-data`）明确
「先积累运行数据再调，别拍脑袋改系数」。**本 change 只修"能不能触发"，不碰"触发得对不对"。**

**为什么必须同时换判据（P3）而不是只改窗口**：
同一个事实（「他多久没说话」）现在有两处实现 —— 推送闸那条用
`getLastUserMessageAt()`（正确、无窗口），衰减这条在 7 天窗口里反查。
只修一处会留下**第三份**同类判据，正是 `eligibility.ts` 头注释在治的病。

**为什么不"把窗口调到 30 天"**：那只是把天花板抬高，下次改阈值仍会撞。
根因是「用窗口查询算一个**无上界**的时间差」，必须换数据源。

## 对账方向确认

- [x] **doc 已声明、impl 没做到** → **改 impl 不改 doc**。spec §11 写的是
      「沉默 ≥ silentAfterDays 开始降」这类语义（衰减**应该**发生），
      现状是永不发生 ⇒ 补实现，**不许把 spec 降级成"不衰减"来迁就现状**
- [x] 涉及 Web API？**否**。`getLastUserMessageAt()` 已是 `MemoryManager` 公开方法
      （`memory-system` §10 已登记），无新端点

## 测试计划

1. **可达性（核心）**：`idle=7` → 不衰减；`idle=8` → **衰减 1.8**；`idle=30` → 衰减 `1.8×23`
2. **哨兵**：`getLastUserMessageAt()` 返回 `null` → 不衰减、不抛、留一条限频日志
3. **等价性**：`idle≤7` 时新旧判据结果一致（防止顺手改了正常路径的行为）
4. **判据同源**：衰减用的 idle 与推送闸用的 idle 在同一时刻取值相同（同一个 mock 下）
5. 回归：`life-service.test.ts` 现有 5 天用例保持通过（它测的是"没跨过就不衰减"，仍然有效）

## 风险

- ⚠️ **修好之后她会真的开始衰减**：这是本 change 的目的，但要预告 —— 长期不说话的账号，
  亲密度会从 30 起、按 1.8/天 往下掉（下限 10）。若线上已有很久没互动的会话，
  上线后第一次 tick 就会看到明显下降。**这是设计行为，不是回归。**
- ⚠️ `getLastUserMessageAt()` 是 SQL 全表查询（带条件索引友好），高频调用需确认没有性能问题
  （`updateIntimacy` 每小时一次，量级无忧）。
