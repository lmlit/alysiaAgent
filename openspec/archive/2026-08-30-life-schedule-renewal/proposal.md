# Change Proposal: life-schedule-renewal

## 元信息

- **日期**: 2026-08-30
- **类型**: MODIFY（改现有行为）
- **状态**: proposed
- **影响 spec**: `ai-life-system`

## 动机（为什么做）

8-29/30 运行日志分析（本地 7.6h + 服务器 33h 停摆实证）发现：

1. **事件密度低**：实测间隔全在默认 2h 附近（1.77h/2.5h/2h），模型建议 next_in_hours 未产生弹性——"间隔表达沉浸"名存实亡
2. **P1-6 真实发生**：服务器 8-28 02:40 后 LLM 生成失败 → `if (!evt) return` 不重排 → **LifeService 静默停摆 33h**，chatPushesToday 恒 0
3. **跨 0 点断链**："今日事件"按本地日期过滤，23:00 睡下 → 0:30 触发时剧情链为空
4. **连续性隐患**：1h 快照节奏下"覆盖间隔补写"引导会诱导 LLM 编造 1h 内的波折（流水账）

## 需求（做什么）

- [ ] **锁续期调度**：成功按模型建议(0.5-8h 钳制)/ 失败 1h 保底 / 异常 try-catch 兜底——锁一定续,永不静默停摆(P1-6)
- [ ] **时段保底**：白天(7-24h) 1h / 夜间(0-7h) 2h——睡觉/安静的夜节奏放慢,减少编造夜间活动
- [ ] chat 日上限 5 → 20（实测问候 3 条/天零错误码,QQ 配额无忧;打扰密度由 1h 冷却+20 上限控制）
- [ ] **补写强度随 gap 渐变**：≤1h 此刻即间隔 / 1-2h 轻引导 / >2h 重补写——幕间 advance 语义不变(每个事件覆盖间隔),短间隔不勉强编造
- [ ] 延续候选连续 ≥3 次 → 强制开新事(防同一件事续写 8h 流水账;零迁移,用连续 internal 链近似)
- [ ] **剧情链 → 近 24h 滑动窗口**(listLifeEvents(1) 天然支持) + 跨天日期标注(昨天23:00) + 上限 8 条——跨 0 点连续
- [ ] 事件日志加 next_in_hours 观测值(验证模型决策)

## 设计决策（怎么做，含备选与取舍）

- **间隔表达沉浸保留**：模型给值 → 尊重(0.5-8h),想聊提前/沉浸延长;不给值 → 规则兜底(时段保底)——两个层次都可靠
- **锁续期 = 容错机制**：`!evt` 分支也续期(1h 保底),tick 异常在 setTimeout 回调 catch 续期——"锁一定会续,只是续多长不同"
- **重补写场景** = 沉浸(模型 3-8h) + 重启(长 gap) + 夜间(2h 间隔)——不是故障(故障 1h 后重试,gap 反而小)
- **延续链计数用近似**：最近事件连续 internal ≥3 视为续写过长(零 DB 迁移;continuation_of 未持久化,不为此加列)
- **"今日事件" → 近 24h**：跨 0 点连续性;ID 集合窗口化后延续候选的 todayIds.add 特判可删
- chat 上限按天重置不变;问候去重按天不变

## 对账方向确认
