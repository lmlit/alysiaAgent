# Change Proposal: server-data-sync-script

## 元信息

- **日期**: 2026-08-28
- **类型**: NEW（新功能）
- **状态**: archived
- **影响 spec**: `memory-system`（新增运维工具，不改数据模型）

## 动机（为什么做）

本地（开发机）与服务器（121.41.111.120，云端 appid 24h 在线）是两个独立实例，数据各自积累。用户实际使用基本都在服务器（本地无法长时间部署），**服务器的 alysia.db 是权威数据**（互动/画像/生活/自写内容全部在服务器上积累）。

需求：手动脚本把服务器数据同步到本地，本地开发/测试时用同一份数据（两边的用户都是用户本人，全量同步即可）。

## 需求（做什么）

- [ ] `scripts/sync-from-server.sh`：服务器在线导出 DB → scp 回本地 → 备份旧库 → 替换 → 提示重启本地服务

## 设计决策（怎么做，含备选与取舍）

| 决策点 | 结论 | 备选（否决理由） |
|--------|------|------------------|
| 同步粒度 | **整库替换**（alysia.db 全量——用户画像/生活/自写/会话全在一个库） | 表级合并（冲突处理复杂、增量逻辑要维护；用户场景"服务器权威"整库最可靠） |
| 导出方式 | 服务器容器内 `better-sqlite3` 的 `backup()` API（**SQLite 在线备份，不停机**，一致性安全） | 直接 cp 主库文件（WAL 模式下主库与 wal/shm 分离，复制可能不一致） |
| 本地旧库 | 替换前备份 `alysia.db.bak-<时间戳>`（可回滚） | 直接覆盖（丢本地数据，无后悔药） |
| 本地服务 | 脚本检测 6185 是否在跑 → 在跑则警告并跳过替换（提示先停） | 自动杀进程（危险，用户可能有会话） |
| 触发 | 手动运行脚本（用户确认的触发方式） | 定时/启动自动（用户明确选手动） |

## 对账方向确认

- [x] 不涉及 spec 数据模型变更——纯运维工具（脚本不进运行时，放 `packages/server/scripts/`）
- [x] 不涉及 Web API

## 测试计划

- 脚本 dry-run 流程：服务器导出文件存在 + 本地备份生成 + 替换后 DB 打开校验（PRAGMA integrity_check + 表计数对比）
- 真实跑一次：服务器数据 → 本地可见（抽查画像/生活事件/digest 数量）
