# Change Proposal: retell-events-in-her-voice

## 元信息

- **日期**: 2026-10-25
- **类型**: MODIFY（推送链路：一段生成 → **两段**）
- **状态**: **archived**（2026-10-25 已部署；转述实测 162 字日记 → 25 字口语，过校验）
- **影响 spec**: `ai-life-system`（推送判定 §、事件生成 §）
- **用户原话（动因）**：「她生成的事件，应该再过一轮模型，**以她的视角讲给我听**才行」

## 动机：一段调用同时承担两种体裁，必有一方被污染

| 字段 | 谁要的 | 体裁要求 |
|---|---|---|
| `content` | **她的日记 / 记忆** | 2-4 句生活切片、具体时辰、平凡物件、小动作、可有小意外 |
| `message` | **推给你的话** | 口语、像发微信、短、有钩子 |

两者塞在同一次 `generateEvent` 调用里，实测出现两种劣化：

1. `message` 也带小说味（「空布袋搭在肩上轻飘飘的，倒是石阶上的水气把裤脚沾得凉」）
2. **`message` 缺失时静默回落 `content`** —— 于是**她的日记被当作消息发给你**
   （`pushText = evt.message ?? evt.content`，且 `postCheck` **从不校验 `message`**，
   这条路上没有任何东西会报错）

## 需求（做什么）

推送前**再过一轮模型**，任务是**转述**而不是创作：

- [x] 新增 `LIFE_RETELL_PROMPT`：输入＝**已发生的事实**（不许编新情节），
      输出＝**对你说的一句话**（1-2 句 / ≤50 字 / 第二人称 / 一个具体细节 / 不写动作与环境）
- [x] `LifeService` 新增 `spokenText()`：**三层逐层降级，绝不回落 `content`**
      | 层 | 来源 | 条件 | 日志 |
      |---|---|---|---|
      | ① | `retellEvent`（第二段模型） | 注入了且过 `checkRetell` | `via=retell` |
      | ② | 事件自带 `message` | 存在且过**同一套**校验 | `via=message` |
      | ③ | —— | 都不合格 ⇒ **这次不打扰**（降级 internal） | `no spoken text (...)` |
- [x] `checkRetell()` 硬校验：非空 / ≤70 字 / 不许抄叙述（开头 20 字相同）/ 不许 `*动作*`、
      `（动作）`、markdown
- [x] 采样槽 `life.retell`（`temperature 0.85`、**`max_tokens 512`**）+ 预算现场日志
      （`finish=` / `tokens=` / `reasoning=` / `content=N字`，与 KI-1 同一判据）
- [x] 推送日志加 `via=`：**能看出这一条到底走的是转述还是 message**

## 关键决策

**为什么保留第 ② 层（校验过的 `message`）**：`message` 本来就是"对轻月说的话"字段，
它的问题从来不是"存在"，而是**没被校验、缺失时静默回落叙述**。校验它 + 不回落 content，
洞就堵上了；同时没注入生成器的场景（单测、尚未升级的部署）仍可工作。

**为什么 `retellEvent` 缺失时不报错、只是不推**：转述是**推送的前置条件**。
宁可不发，也不要发日记 —— 这正是用户抱怨的东西。

**为什么新槽必须写 `max_tokens`**：本仓推理模型会先花 200-300 token 在 reasoning 上，
且与可见内容共用预算。`life.generateEvent` 至今没有这个字段（KI-1 登记在案），新槽不留同样的坑。

## 对账方向确认

- [x] **改 impl**：spec 早已声明 `message` 才是推送内容、content 只入库；impl 却回落 content
- [x] 涉及 Web API？**否**

## 测试计划

`life-service.test.ts`（85 例，含新增）：

- ★ 注入 `retellEvent` → 推送的是**转述结果**，且转述输入含「你刚做的事」+ 关系现状
- ★ **无 message 且无转述 → 不推送**（原用例「回落推 content」已按行为变更重写）
- ★ 转述超长（77 字）→ 判不合格，不推送
- ★ 无生成器但 `message` 合格 → 仍推 `via=message`
- 既有 4 处 chat fixture 补上 `message`（chat 事件本该带）

全量：**165 文件 / 1938 用例**。

## 风险

- ⚠️ 每条推送**多一次 LLM 调用**（每天上限 5 条 ⇒ 最多 5 次/天）。可接受。
- ⚠️ 转述失败会**少发一条**（这是有意的取舍：宁可少发，不发日记）。
- ⚠️ 仍**不经过**聊天的 `CHAT_BREVITY_DIRECTIVE`：两条链路prompt 各自独立，
      但本次已把"像发微信 / ≤50 字 / 不写动作"写进 `LIFE_RETELL_PROMPT`，约束口径与聊天一致。
