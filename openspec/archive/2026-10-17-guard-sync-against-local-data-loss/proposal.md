# Change Proposal: guard-sync-against-local-data-loss

## 元信息

- **日期**: 2026-10-17
- **类型**: FIX（工具防护 / 数据安全）
- **状态**: **archived**（2026-10-17 propose → apply → archive）
- **影响**: `packages/server/scripts/sync-from-server.sh`、新增 `scripts/check-sync-data-loss.cjs`
- **影响 spec**: 无（工具层，非系统契约）；但记入 `docs/KNOWN-ISSUES.md` 的 KI-20 关联备注

## 这条要解决什么（真实事故，不是假想）

`sync-from-server.sh` 是**整库覆盖**本机库的。**2026-10-15** 那次同步把本机独有的
**730 条 dsh 事件**换成了服务器的 QQ 数据 —— 本机 dsh 血脉从此**只剩备份**。

这件事**直到 2026-10-17 做 KI-20 存量修复时才被发现**（当时以为是"污染在服务器上"，
查了才发现服务器是纯 QQ 库、污染只活在本机备份里）。

**脚本有"先备份"是好的，但备份不解决问题**：没人会去翻一个自己**不知道存在**的备份。
缺的是「**覆盖前算出并说出来：你将失去什么**」。

## 需求

- [x] **R1**：新增只读体检工具 `scripts/check-sync-data-loss.cjs`
      —— 比较「本机库」与「即将覆盖它的远端库」，报出**本机独有**的事件/会话
- [x] **R2**：退出码可被脚本消费：`0`=没有独有数据、`1`=**有**（调用方应中止）、`2`=用法错
- [x] **R3**：`sync-from-server.sh` 在**替换之前**调用它；非 0 则**中止**，
      除非显式 `ALYSIA_SYNC_ALLOW_LOCAL_LOSS=1`
- [x] **R4**：中止时给出**两条出路**（先合并 / 显式接受丢失），而不是只说"不行"
- [x] **R5**：连带显示**派生状态**差异（facts / character_facts 计数）供人判断
      —— 但不以它阻止同步（它不是"独有数据丢失"）

## 设计决策

### D1 判断逻辑放 Node，shell 只做调用与拦截

bash 在这个仓库里**没法测**（本机 `bash` 甚至是没装发行版的 WSL 桩）。
放 Node 就能用真实数据测，shell 侧只剩 `if ! node …; then 中止`。

### D2 判据是「**本机独有**」而不是「谁更完整」

服务器数据更完整**不等于**本机独有的那部分不重要 —— 10-15 那次正是这么丢的
（远端 1828 事件 vs 本机 1689，看起来"远端更全"，但本机有 **884 条远端没有的**）。

### D3 不自动合并、不自动删 —— 只报告 + 拦

自动合并 = 让工具替人决定"什么该进生产"。本项只负责**把话说清楚**。

## 测试计划

用**真实的历史事故数据**跑两个场景（`scripts/check-sync-data-loss.cjs`）：

| 场景 | 输入 | 期望 |
|---|---|---|
| ① 本机有 dsh、远端没有（**= 10-15 那次**） | `--local bak-20261015-213807` `--incoming 远端快照` | **exit 1**，报出 884 条独有事件（dsh 730 / qq 146 / webui 8）+ 32 条独有会话 |
| ② 本机是远端的子集 | `--local alysia.db` `--incoming 远端快照` | **exit 0** 放行 |

外加：`bash -n` 语法检查（用 Git 自带的 bash）、以及用**脚本里完全相同的调用方式**
（cwd=`packages/core`、相对路径）跑一遍确认接线正确。
