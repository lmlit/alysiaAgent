# Change Proposal: put-dropped-turns-back

## 元信息

- **日期**: 2026-10-20
- **类型**: FEATURE（**B 类：行为必变**，默认启用，可退回）
- **状态**: `applied`
- **影响 spec**: `alysia-architecture` **§6.5（新增）**；`docs/Web-API-Design.md` 登记新 core 方法
- **上游**: `observe-and-hold-context-compaction`（§6.4，已归档）

## 这条要解决什么

§6.4 修的是"摘要失败时别急着截断"。但**截断本身**丢掉的东西依然没了：

```
上下文超预算 → truncate() 丢掉最旧的 turn → 那些对话彻底消失
（不进摘要、不进记忆，只在 DB 里，会话结束才可能被摘到）
```

长会话中段，她真的不记得刚才聊过什么。而 `truncate()` 以前返回 `void`
—— 连"丢了哪些"都拿不到，所以"压回去"无从谈起。

## 做法

1. **`truncate()` 返回被丢弃的轮次**（纯改动，可测）
2. **攒批**：不足 `4 条` 且不足 `1200 字` → 先攒着（长会话每步只丢 1 条，逐条压 = 一步一次 LLM 调用）
3. **压**：`AgentHooks.summarizeDroppedTurns`（core 不持有 LLM，分层）
4. **插**：摘要作为「更早的对话（已压缩）」插到 `system` 之后
5. **累积**：第二次压缩把「旧摘要 + 新丢弃」再压一遍，**替换**同一条消息

## 为什么用 hooks 而不是让 runner 直接调 memoryManager

- `AgentRunner` 现在只有 provider/tools/hooks 三个依赖，加 `memoryManager` 会牵动
  所有构造点与 30+ 测试（**为功能付假成本**）
- `AgentHooks` 已存在且就是为"外部想插一脚"设计的
- 好处：**未实现该 hook ⇒ 完全保持旧行为**，回滚 = 删掉实现

## ★ 可证伪判据（写进 spec §6.5.2）

这套机制**能跑通 ≠ 让人更聪明**。上线后必须验：

1. 造一段足够长的会话（>3 次压缩），记下**中途**发生的三件事（承诺/决定/待办）
2. 会话继续到很远之后再问那三件事
3. **判据**：至少 2 件答对 ⇒ 有效；只答得出最近那件 ⇒ 压缩退化成"更长一点的窗口"，
   应退回（不实现 hook）

**不许用"看起来还在"当验收。** 压缩最大的风险不是丢，是**编造**
（把没发生的事总结成发生过）—— 比遗忘更糟，因为没人会怀疑。

## 护栏

| 护栏 | 值 | 防什么 |
|---|---|---|
| 攒批 | 4 条 / 1200 字 | 一步一次 LLM 调用 |
| 摘要上限 | 800 字 | 摘要自己撑爆上下文 |
| 替换而非追加 | — | 同上 |
| 空返回不插 | — | 插一个空块 |
| 失败留痕 | warn 限频 | "丢了"与"没丢"同形 |
| 槽位 | `profile.deepRewrite`（**纯文本**） | 默认槽 json_object ⇒ 400 |

## 不做什么

- 不做"按话题切分压缩"（要 topic 检测，独立能力）
- 不改 `length/3` 的估算口径（§6.4 契约 1 的已知债）
- 不做摘要质量打分（没有可靠判据前不做）

## 回滚

删掉 `llm-agent` 里 `summarizeDroppedTurns` 的实现即可 —— `AgentRunner` 会走旧路径（直接丢）。
无需改 core 任何代码。
