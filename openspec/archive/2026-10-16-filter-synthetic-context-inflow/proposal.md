# Change Proposal: filter-synthetic-context-inflow

## 元信息

- **日期**: 2026-10-16
- **类型**: FIX（修 bug；**取证已完成**，结论见下）
- **状态**: **archived**（2026-10-16 完成 propose → apply → archive；未部署）
- **影响 spec**: `dsh-adapter` **§2.5 扩写**、`alysia-architecture` **新增 §4.3.1**
- **来源**: 修复计划「第二批」第 1 项；`docs/KNOWN-ISSUES.md` **KI-20**

## 这条要解决什么

dsh 的「runtime context 快照」被当成**用户消息**回传入库，形成**回流闭环**。

**现象**（2026-10-02 实测，KI-20）：全库 **116 条** events 的 payload 以

```
Current runtime context. This snapshot supersedes earlier runtime-context snapshots.
```

开头，内容是 `[角色设定]`（人格参数）+ `[关于你]`（完整画像）+ `[关于我]` ——
却被标成 `role: 'user'` 入库。单个主会话 `dsh:session-29b9865c` 里出现 **35 次**。

**两条自指回路**：

1. **画像回吸**：`ProfileExtractor` 从画像里「重新学」出画像 ——
   facts 的 `valid_from` 被刷新、`source_event` 指向这些事件。
   本次 `purge-subagent-pollution` 里那些「内容为真但溯源指向子会话」的 facts
   就是这个机制产出的（子 agent 的 prompt 里同样带这段快照）。
2. **人格放大**：`PersonaAdapter` 从这段文本再触发 hints ——
   实测 15:21:12 一条 hint 的证据是「记忆里轻月明确指出过『太整齐、分点…』」，
   即**记忆触发记忆**。

**★ 它与「子 agent 回传」不同源**：这是**主会话也有的独立缺陷**，
`exclude-subagent-sessions-from-bridge` 那次的过滤**解决不了它**。

## ✅ 取证已定案（2026-10-16）：**dsh 合成注入**，⇒ **该滤**

> 原始证据与复现步骤见 `tasks.md`「取证记录」。**结论：不是真实用户输入。**

**判据不是文本前缀，而是"这句话由谁生成"** —— 找到产它的那行代码即可定案。
`E:\dsh\resources\app.asar` 里该字符串**恰好出现 1 次**：

```js
return `Current runtime context. This snapshot supersedes earlier runtime-context snapshots.\n\n${body}`;
```

**前缀是 dsh 的字面量，`body` 是变量** ⇒ 这是 dsh 的一个**包裹函数**：
它把任意 `body` 包上前缀后注入会话。因此：

1. 那 116 条事件的**开头**必然由 dsh 产生（与用户发言无关）；
2. **机制上也解释得通**：注入的是会话里的**一条 user 角色消息** ⇒
   adapter 的「用户消息」监听器照样会捕获并回传 ⇒
   所以**主会话也有**（不是子 agent 专属），且单个会话能出现 35 次；
3. 本次会话（2026-10-16）里 dsh **当前版本仍在这么做**：它注入了一段
   `body` 为「文件策略 / 审批策略」的 runtime context ——
   可见 `body` 内容**与用户发言完全无关**（那段讲的是沙箱模式与审批开关）。

**⇒ KI-20 原文那条注意项（"先确认是合成注入还是真实用户输入"）已满足，实现方向成立。**
下面的 R2–R6 与 D1（**提取侧打标**，不硬删事件）**按原方向执行**。

**⚠️ 仍未验证的（不许当成已验）**：
- 我验证的是**前缀的产生者**，**不是**那 116 条生产事件的完整 payload 形态
  （它们的 `body` 是 `[角色设定]`/`[关于你]`/`[关于我]`，属**间接**证据：那些块本就是 alysia 注入的）。
- `body` 是变量 ⇒ 过滤**必须按"前缀包裹"整体判定**，**不得**假设 body 长得像什么、
  更**不得**把 body 当作她的发言去学习。
- R3 仍然成立：**前缀只是兜底判据**（dsh 改文案就会失效），主判据要看事件类型与来源标记。

## ⚠️ 动手前必须先回答的问题（**已由上一节回答**）

> KI-20 原文的注意项：「**先确认这段文本是 dsh 合成注入还是真实用户输入**（前者才该滤）」。

**已定案 = 合成注入。** 原始取证手段留档如下（供将来复核同类问题）：

1. **dsh 侧**：`~/.dsh/sessions/<工作区>/session-*/session.v4.jsonl.zstd` 是**多帧 zstd**
   （按魔数 `28 B5 2F FD` 切帧逐段解压，见 `dsh-adapter` §5），
   里面有会话事件的**原始记录** —— 能看清这条 `user/message` 是**谁**产生的、
   `data` 的形状是否与真实用户输入一致（真实输入走 `data.message.content` 块数组）。
2. **更省事且不碰任何用户数据的一条**（本次实际用的）：**在 dsh 自己的产物里搜这句话**。
   它若出现在 dsh 的 bundle / 源码里，就说明**是 dsh 生成的**，不必去看会话内容。
3. **判定分叉**：
   - **dsh 合成注入** → **该滤**（✅ 本次结论），按下面方向实现；
   - 真实用户输入 → 不许滤，本 change 应改为「提取侧降权/打标」或关闭并**更正 KI-20 描述**。
4. 取证记录必须写进本 change 的 `tasks.md`（结论 + 原始证据片段），
   **不许只写结论**——本项目已因「先写错再纠正」吃过一次亏（见 KI-21 的更正节）。

## 需求（做什么）

> 以下按「取证结论 = **合成注入**」这个前提写；若取证结果相反，本节的实现项作废，
> 只保留「更正 KI-20 描述」这一项。

- [ ] **R1 取证**：判定该文本的来源（合成 vs 真实），结论 + 证据落 `tasks.md`
- [ ] **R2 拦截**：合成内容**不得**作为普通用户发言参与画像与人格学习
- [ ] **R3 判据优先用事件类型与来源，不只用文本前缀** ——
      前缀判据是**脆的**（文案一改就失效），只能当兜底
- [ ] **R4 区分「事件是否保留」与「是否允许学习」**：
      事件本身**仍可入库**（它是真实发生过的一次注入，删掉会破坏事件日志的不可变性），
      要拦的是**它进入学习管道**
- [ ] **R5 可观测**：跳过学习必须**留痕**（限频），不许静默——否则「滤掉了」与
      「本来就没采到」同形
- [ ] **R6 不误删真实对话**：用户**引用或粘贴**类似文本时不得被误判（回归用例）

## 设计决策（怎么做，含备选与取舍）

### D1 优先在**提取侧**打标，而不是在 adapter 侧硬删（待取证后确认）

KI-20 给了两条路：① adapter 侧按 payload 前缀过滤；② 提取侧对
`Current runtime context` 开头的 payload 打 `skip_profile`（**现成机制**）。

倾向 ②（提取侧）的理由：

- **事件日志按 CLAUDE.md 定义是「不可变」的**——adapter 侧丢弃等于让"发生过的事"消失，
  而这类注入的频率与形态将来还要复盘（没有记录就无法复盘）；
- 「是否允许学习」是**学习管道的语义**，就该由学习管道判定；
- 位置更靠近 `ProfileExtractor` / `PersonaAdapter`，一处生效覆盖两条回路
  （画像回吸 + 人格放大）。

**被否决：adapter 侧静默丢弃**——它同时毁掉 ① 可复盘性与 ② 事件日志的不可变性。

**被否决：只靠文本前缀**（见 R3）——文案一改就静默失效；
前缀只能作为**兜底判据**与**回归用例的输入**。

### D2 存量数据**不在本 change 处理**（单独评估）

已入库的 116 条事件与由它们产出的 facts 需要一套**数据修复**方案
（与 `purge-subagent-pollution` 同类）。本 change 只保证**从此往后**不再回流；
存量修复**另开**（`fix-reflection-insight-misroute` 的先例：代码修复与数据迁移分开做、
且**部署状态要单独记录**）。

### D3 与「子 agent 过滤」的关系：两道独立的闸

`exclude-subagent-sessions-from-bridge` 拦的是**会话来源**（`header.origin`），
本 change 拦的是**消息内容/来源标记**。**互不替代**，都要有。

## ✅ 落地结果（2026-10-16）——与上面草案的**两处有意偏离**

1. **文本前缀从「兜底判据」改为「不作判据」**（原 R3 的措辞）。
   理由：前缀与 **R6**（用户粘贴类似文本不许被误判）**直接冲突**；
   结构化判据按定义不会误伤，且已被证明覆盖全部已知样本
   （116 条都出自同一个 `project()` 调用点）。
   ⇒ 这是**主动收窄**，不是遗漏；判据唯一来源是 `source.kind`。
2. **多堵了一条泄漏路径：摘要**。原草案只提画像与人格；
   实现时发现 `SessionEndProcessor` 用全部 messageEvents 组 dialogue、**不看 `skip_profile`**
   ⇒ 合成文本会进摘要、日后被召回并回灌。已排除 `synthetic`
   （**只排 synthetic**，不动群聊 NPC 的既有行为）。

另：顺带修掉 `tests/memory/integration/processors.test.ts` 里一个
**构造调用少传一个参数**的既有缺陷（测试一直是绿的，但跑的不是它以为的那条路）——
根因是 `tsconfig.json` 只 `include: src/**/*.ts`，**测试不参与类型检查**。

**实现与证据见 `tasks.md`。**
