## 动机（为什么做）

dsh 侧的记忆回传（`packages/dsh-adapter/src/index.ts` 的 `installBridge`）有三处已被证据坐实的缺陷。
三条都在**同一条链路**（队列 → 回传 → 结算）上，且互相纠缠：结算的修复依赖队列串行化，
身份判定的修复又落在同两个 handler 里，所以合并为一个 change（见「为什么放在一起」）。

### ① 队列无法排空：批次超上限 + 永久拒收被当临时故障

- 适配器把**整个 `pending` 数组**当一个请求发出去（`index.ts:197`，无分片），
  而服务端单批上限是 **200**（`packages/server/src/ingest.ts:14` `MAX_INGEST_BATCH`），
  适配器自己的队列上限是 **500**（`index.ts:279` `MAX_PENDING`）。
  ⇒ 积压一超过 200 条，服务端一律 413。
- `AlysiaClient.request` 把**任何** `!resp.ok` 都归成失败返回 `null`（`alysia-client.ts:144-149`），
  `flush()` 又把 `null` 解释成「alysia 不可达」，于是把批次**原样放回队首**（`index.ts:198-207`）。
  ⇒ **413 是永久拒绝，却按可重试故障处理**：之后每次 flush 都用**同样的输入**重复同一个 413，
  **永远不可能成功**。这不是「批次太大」的附带现象，是一个独立的**故障分类**缺陷。
- 加重项（原计划未记）：`noteFailure` 连续失败 3 次后**闭嘴**（`alysia-client.ts:166-171`），
  所以队列**永久卡死**时日志会自己安静下来，而 `dropped` 只在 push/flush 时各说一句。
  这正是本项目反复栽的「静默掩盖」形态。

### ② KI-24 🔴 结算抢跑：会话最后一轮**永久**进不了摘要

- `turn/end` → `void flush()`（不 await，`index.ts:232-233`）；
  `session/disposed` → `void (async () => { await flush(); await extractSession() })()`（`index.ts:267-275`）。
  两条链没有任何互斥，而 `flush()` 开头就 `const batch = pending; pending = []`（`index.ts:194-196`）——
  上一批**在飞**时，`disposed` 的 `flush()` 看到空队列**立刻返回**，`extractSession` 随即开跑。
- **为什么后果是永久的**：服务端结算窗口是 `created_at >= anchor`，
  `anchor = 该会话最新摘要的 ended_at`；新落库的摘要行 `ended_at = 服务端当时时间`。
  迟到事件的 `created_at` 取自 **dsh 的事件时间**（`index.ts:257`），**早于**那条摘要的 `ended_at`
  ⇒ 落在**下一次窗口之外，永远不会被摘要**。且摘要行是 `summary_status='ok'`，
  `retryFailedSummaries()` **不会补**。⇒ 不是「晚一点摘到」，是「永久摘不到」。
- 丢失的是**摘要与画像这一层**；事件本身仍在事件表里，`read()` / 向量召回仍捞得到——
  所以更难察觉。

### ③ KI-23 🟠 取不到会话 id 时退化 `dsh:unknown`，多个真实会话挤进同一个桶

- `sessionIdOf()` 取不到 id 时返回字面量 `'unknown'`（`session-id.ts:29`，注释自陈
  「宁可退化到 unknown 也不要抛」），调用方**照常继续**：刷缓存、`session_id: 'dsh:unknown'`、
  `extractSession('dsh:unknown')`（`index.ts:225/245/273`）。
- ⇒ 多个不同真实会话的**事件、摘要、画像全部混进一个桶**（等价于已经修掉的「子 agent 污染」，
  但更难发现）；`summaryAnchor()` 会拿该桶的最新摘要当锚点 → 窗口跨会话错乱。
- 与「子 agent 会话」的处理**不一致**：那一类是 **fail closed**（跳过，`skipSubagentSession`），
  这一类却是 **fail open**（照常写）。dsh 已换过一次插件机制，`Session` 形状一旦变化，
  这条退化路径就会**静默开启**。

## 需求（做什么）

- [ ] **R1 分批**：回传按服务端上限分批发送；积压 201 条 / 500 条都能排空
- [ ] **R2 串行化**：同一队列只允许一个发送流程在途；后续触发**复用**在途流程，不另起一条
- [ ] **R3 故障分类**：区分**可重试**（连接失败 / 超时 / 5xx）与**永久拒收**（4xx）；
      永久拒收**不进重试队列**，也不阻塞同批其他合法事件；部分成功（`accepted` + `rejected`）如实上报
- [ ] **R4 不静默丢弃**：明确队列上限、丢弃规则与诊断信息；卡死/丢弃的诊断**不受失败降噪影响**
- [ ] **R5 KI-24**：会话关闭时**等待该会话已排队与在途的消息确认落库**；回传失败时**不**宣布结算完成、
      也**不**无条件继续提取；提供**失败后的再次结算入口**，不依赖「下一次刚好有消息」
- [ ] **R6 KI-23**：身份不明时**不回传、不结算**，输出**限频**诊断；不阻断 dsh 自身的聊天与工作；
      **不**临时生成随机 id 掩盖上游契约问题
- [ ] **R7 契约**：更新 `openspec/specs/dsh-adapter/spec.md` §2.5，把上述行为写成可验收的契约

## 设计决策（怎么做，含备选与取舍）

### D1 分批放在**投递队列**里，不放在 `AlysiaClient`

队列拥有重试/丢弃策略，也需要**逐批**的结果来做分类，所以由队列切批、逐批调用客户端。
被否决：在 `AlysiaClient.ingest()` 内部自动分片——那会让「一次调用 = 一次请求」的语义消失，
调用方再也无法把「这一批被永久拒收」归因到具体事件，且重试边界变模糊。

### D2 `AlysiaClient.ingest` 的返回值改成判别式联合（**行为变更**，故写进契约）

现在的 `IngestResult | null` 把「服务端明确拒绝」和「根本连不上」压成同一个 `null`，
**信息在传输层就丢了**，上层再怎么修也分不出来。改为：

```ts
type IngestOutcome =
  | { kind: 'ok';        accepted: number; rejected: string[] }   // 含部分成功
  | { kind: 'permanent'; reason: string }                          // 4xx：重试无用
  | { kind: 'unreachable'; reason: string }                        // 连接失败/超时/5xx：可重试
```

`null` 的旧语义**取消**（空数组仍返回 `{kind:'ok', accepted:0, rejected:[]}`）。
「**永不抛出**」这条不变量**不变**——`unreachable` 仍不抛，只记日志。
代价：`tests/alysia-client.test.ts` 有 3 处断言要跟着改（`void` 返回 `null` 的旧契约已作废）。
被否决：加一个 `ingestDetailed()` 并行方法——两套入口必然分叉，那是 KI-3/KI-9 已经栽过的坑。

### D3 串行化用**在途 promise 链**，不引入锁/队列库

`let flight: Promise<void> = Promise.resolve()`，`scheduleFlush()` 把新的排空挂到链尾并返回它。
`disposed` **await 整条链**（含在途那批）后再结算。
被否决：引入 `p-limit` / 信号量——单进程单队列，一个 promise 链就够，且无新依赖。

### D4 永久拒收的处理：**整批判死**，逐条上报

服务端 4xx 是**整批**拒绝（如 413 批太大、400 body 不合法），没有逐条信息，
所以只对**已通过校验的批次**做分类；`{kind:'ok'}` 里的 `rejected[]` 才是逐条永久拒绝。
两类都**不计入待重发队列**，只计数 + 上报（含前几条原因），避免无限重试无效事件。
413 属**契约漂移**（上限被下调 / 适配器版本旧），必须**响亮**报出而不是降级处理。

### D5 KI-24 的「再次结算入口」= **挂起结算集合**，不新增对外接口

`disposed` 时若该会话仍有未确认落库的事件，则把它记进 `pendingSettlements`，
在**下一次成功排空后**重试结算（也保留在后续 `turn/end` 后重试）。
设**有限次尝试**，耗尽后打一条**明确失败**的日志（含会话 id 与原因），
不再静默——「没结算」必须可见。
被否决：新增服务端接口做「两段确认」——服务端当前只有「按锚点结算」一个语义，
加确认接口要动 `MemoryManager` 契约，超出本 change 范围（记入「后续」）。

### D6 KI-23 走 **fail closed + 限频诊断**，与子 agent 同一条纪律

`sessionIdOf()` 的返回类型改为 `string | null`（**去掉 `'unknown'` 字面量**），
调用方必须显式处理 `null`。`unknown` 不再是「一个合法但劣质的 id」，而是「没有 id」。
限频：每个**事件类型**首次出现打一行 `warn`，之后静默计数（避免坏上游把日志刷爆）。
另在服务端 `/api/ingest` 加**第二道闸**：字面量 `dsh:unknown` 直接拒收
（`'unknown'` 永远不是真实 dsh 会话 id）。两道闸的分工：适配器**不产生**，
服务端**不接受**——任一失效都有另一道挡着，且服务端的拒绝原因是具体的。

### D7 事件日志的重复投递语义（KI-12，在 `fix-store-write-trace` 内实现）

本 change **不**改 `EventStore`。但为避免两处对「重复投递」的理解分叉，先把口径写在这里：
CLAUDE.md 定义 Event Log 为**不可变**，所以同 id **不同内容**时**不覆盖**、保留原事件并
**响亮报冲突**；同 id **同内容**为幂等空转。
⇒ 这正是 KI-12 的方向（补上 `archived` 等状态列不被重置），**与本 change 的 R3/R4 不冲突**。

## 为什么放在一起（对「一个 change 只做一件事」的说明）

治理宪法要求「小步」。本 change 的三项**共用同一段代码与同一个测试夹具**：
`installBridge` 的两个 handler、`flush()`、以及一个「假 server」夹具。
拆成三个 change 会产生**顺序耦合**（R2 的串行化是 R5 的前提；R6 与 R5 改同一对 handler）
和**重复的夹具工作**，且第一个 change 单独验证时会测一条**注定要再改一次**的路径。
故合并立项，但 tasks.md 按 T1/T2/T3 分组、**逐项独立验证**，每组都有自己的复现测试。

## 对账方向确认

- [x] 与现有 spec 是否冲突？——**扩写**。现 §2.5 只声明了「事件 → 回传 → 结算」的存在与
      「子 agent 一律跳过」，**未声明**批次上限、串行化、故障分类、结算时序、身份缺失行为。
      本 change **新增契约**（R1–R6），不改既有条款方向。
- [x] 方向判断：`docs/KNOWN-ISSUES.md` 的 KI-23 / KI-24 是**缺陷登记**（行为不对），
      非 doc/impl gap。修复方向 = **改 impl**，同时**补 doc**（把新契约写进 §2.5）——
      **不**把 KI 描述降级去迁就现状。
- [x] 涉及 Web API？——**涉及，但无新增端点**。改动的是 `/api/ingest` 的**调用侧行为**与
      一处**服务端拒收规则**（`dsh:unknown`），请求/响应形状不变（`{events}` → `{ok,accepted,rejected}`）。
      `docs/Web-API-Design.md` 无需新增方法；若其收录了 `/api/ingest` 的拒收原因清单，则同步补一条。
- [x] 契约漂移检查：`DSH_SESSION_PREFIX` 的两份字面量（适配器 / 服务端）已有测试钉住，本 change 不动它。

## ⚠️ 动手前的提醒

- R3 是**行为变更**：`ingest` 返回类型变化会影响所有调用方与测试（已清点：仅 `flush()` 与
  `tests/alysia-client.test.ts` 的 3 处断言）。
- R5 会**增加**结算触发次数 → 必须做挂起结算**去重**，否则会造出 KI-19 的新实例。
- 「永不抛出」是 dsh 侧通道的**根本不变量**（alysia 没起是常态）：任何新增分支都不许破坏它。
- 别把 `pending` 的上限删掉——它是长期不可用时的**内存保护**，本 change 只让它**不再静默**。
