# Change Proposal: fix-memory-context-ordering

## 元信息

- **日期**: 2026-10-16
- **类型**: FIX（修 bug，行为变更：乱序晚归的旧检索结果现在会被**丢弃**）
- **状态**: **archived**（2026-10-16 完成 propose → apply → archive；未部署）
- **影响 spec**: `dsh-adapter` §2.2（记忆 context 的「缓存 + 后台刷新」加一条乱序契约）
- **来源**: 修复计划「第三批：运行可靠性与安全收口」的「缓存乱序」项

## 这条要解决什么

**预热晚归时，会把更新的「话题刷新」结果覆盖掉 —— 那一轮她看到的记忆比上一轮还旧。**

记忆 context 有**两条独立链**，各自 `.then(setMemoryContext)`：

| 链 | 触发 | query | 典型耗时 |
|---|---|---|---|
| **预热** | 插件挂载（`apply()`） | **空串**（只取 `[关于你]` 等不依赖 query 的块） | 启动那一波，最慢 |
| **刷新** | `user/message` 到达 | **用户原话**（话题相关） | 通常更快 |

而写入口只有一个、**谁后到谁生效**：

```ts
const setMemoryContext = (raw) => { if (raw) memoryContext = withRecallHint(raw); };
void sharedPrewarm(...).then(setMemoryContext);              // 更早发起
void refreshMemory(text);                                    // 更晚发起，可能更早返回
```

⇒ 预热**更早发起、更晚返回**时，它落地会把话题刷新的结果**盖掉**。
用户侧表现：**刚说完「我家猫最近怎么样」，这一轮拿到的却是启动时的通用画像快照**，
而且**没有任何痕迹**（两处都成功，日志上看不出顺序问题）。

这是典型的**乱序响应**缺陷：只按「谁先回来谁生效」写，必然中招。

## 需求（做什么）

- [ ] **R1**：每次**发起**检索时领一个单调递增序号；结果落地时，
      **不比已应用的更旧才允许写入**（后发起的永远赢）
- [ ] **R2**：序号必须在**发起时**领，不能在返回时领 ——
      否则晚归的预热会拿着"最新号"把刷新盖掉（等于没修）
- [ ] **R3**：空结果**不推进**已应用序号（失败/无内容保持旧值，不改变排序状态）
- [ ] **R4**：正常顺序（预热先回、刷新后回）**行为不变** —— 刷新照常覆盖预热

## 设计决策（怎么做，含备选与取舍）

### D1 用「发起即领」的单调序号，而不是时间戳或"比较新旧内容"

- **序号**只依赖本进程内的调用顺序，**不受系统时钟漂移影响**（本项目在别处吃过时间的亏）；
- 比内容"新旧"简单且不需要解析 payload。

**被否决：记录 `Date.now()` 发起时间并比较** —— 同毫秒内的两次调用无法区分，
而启动那一波的多次挂载恰恰挤在同一毫秒。

**被否决：给刷新加"延迟到预热完成之后"** —— 那会把首轮响应拖慢，
且违背 §2.2 的既有设计（provider **必须同步返回**，只能给缓存）。

### D2 落点只在 `setMemoryContext` 一个入口

两条链都已经收敛走它（§2.2 那条「⚠️ 曾经只有刷新走、预热直接赋值」的教训），
所以加序号只需改这一处 + 两个调用点的取号方式。**不新增任何并发原语**。

## 对账方向确认

- [x] 与现有 spec 冲突？——§2.2 只声明了「预热要去重」「失败保留旧值」，
      **未声明**两条链返回乱序时谁生效。本 change **补契约**。
- [x] 方向判断：**缺陷**（行为不对），非 doc/impl gap ⇒ **改 impl + 补 doc**。
- [x] 涉及 Web API？——**不涉及**（这是 dsh 进程内的插件缓存，不经 server）。

## 测试计划

落点：`packages/dsh-adapter/tests/index.test.ts`（复用已有夹具；用"挂住请求、由测试决定谁先返回"精确制造乱序）。

| 编号 | 场景 | 验收 |
|---|---|---|
| C1 | **主症**：刷新先返回并落地 → 预热随后返回 | context **仍是**话题刷新内容；**不含**预热内容 |
| C2 | 正常顺序：预热先落 → 刷新后落 | 刷新照常覆盖（R4 回归） |
| C3 | 回归 | 既有 4 条记忆 context 用例（预热/刷新/失败保留旧值/`bridge:false`）继续通过 |

## ⚠️ 动手前的提醒

- **别把序号领在 `.then()` 里**（R2）——那是这个 bug 的另一种写法，会静默失效。
- **别动"失败保留旧值"**：空结果不推进序号，旧值才保得住（R3）。
