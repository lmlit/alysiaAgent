## 动机（为什么做）

**用户原话**（在我给出 A1 只读看板后）：「A，但是他会**自己触发**看看卡住的进度吗」。

诚实的答案是**不会** —— 工具只在被调用时才跑。而今晚的两次真实故障都是"没人盯着"的形状：

- 任务在 `intent` **空转 7 轮**，直到我手工去看日志才发现；
- 我误搬 `public/` 里的文件，**站点断了约一分钟**，没有任何人/程序发现。

⇒ 需要一层**看门狗**：系统用便宜、确定的判据盯着，异常时**把一条冷事实交给她说**。

## 需求（做什么）

- [ ] `al:watchdog` 模块：每 60s（可配）跑一次只读判据
- [ ] 六条判据（全部来自系统读数）：
  | 判据 | 阈值 | 依据 |
  |---|---|---|
  | 任务 `running/queued` 没动 | ≥20 分钟 | 今晚"空转"的形状 |
  | 新增 `unknown`/`failed` | 立即（只报一次） | 今晚 undici 崩溃那次 |
  | runner 心跳断 | ≥90 秒 | runner 挂了 = 所有活不动，而她完全看不见 |
  | 站点首页非 200 | 宿主侧探测连续失败 | 今晚站点真断过一分钟 |
  | 排队堆积 | ≥3 件或最老 >30 分钟 | "人提交了但没人在跑" |
  | 崩溃循环 | 一小时内重启 ≥3 次 | 见下 |
- [ ] 通知：**优先她自己的说法**（模型措辞），失败回落机械模板
- [ ] 去重：同一问题 **30 分钟**只说一次；**恢复**要再说一次（否则用户以为一直坏）
- [ ] 全程**只读**：不重启、不清任务、不改任何东西

## 设计决策（含备选与取舍）

1. **不让她轮询**（否掉"给她一个定时任务"）：每查一次都是一次模型调用，且她看不到 crontab、
   日志滚动这些系统事实。**系统盯、她说**才是正确分工。
2. **判据只认系统读数**（契约 68：判据取事实，不取自述）—— 不问她"你觉得卡住了吗"。
3. **`unknown`/`failed` 只报一次**：靠"上一轮是否已报过该 key"判断，不靠时间窗（否则一直刷）。
4. **崩溃循环用"开机次数"而不是"uptime 小"**（★ 实现中改的）：
   最初写成 `uptimeSec < 300 ⇒ 报`，结果**每次部署都会先发一条"我刚重启过"的假警报**。
   正确判据是"一小时内重启 ≥3 次"（本轮部署只算一次）。
5. **恢复通知不受冷却限制**，但每个 key 只发一次。
6. **站点可达性由宿主探**：容器够不到宿主 3389，所以 runner 每轮顺手 `GET /` 一次
   （3 秒超时、**必须读掉 body** —— 不读 body 会让 undici 崩，这是今晚踩过的坑）。
