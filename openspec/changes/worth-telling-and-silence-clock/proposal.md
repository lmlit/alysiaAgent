## 元信息

- **日期**: 2026-10-25
- **类型**: MODIFY（推送门的两个缺口）
- **状态**: applied
- **影响 spec**: `ai-life-system`（推送判定 §、两段式 §）
- **来源**: 回到 whale 话题 → 对照它的 VISION 表 → 发现我们「有配额、没有判断」

## 动机：对照 whale 的 VISION**

whale 用六句话解释"她要长成什么"，每句落到一处代码。其中两条戳到我们：

| whale | 我们 |
|---|---|
| 分享判据是「**值不值得占用主人一次注意力**」 | 只有 `type==='chat'` + `can_contact` + 日上限/冷却/档位——**判的都是"能不能发"，不是"值不值得发"** |
| **沉默衰减**：3 天开始降、7 天归零 | 亲密度也在"沉默→少说话"，但**慢**：decay 1.8/天 ⇒ 82→70 要 7 天、→40 要 23 天、→25 要 32 天 |

## A. 「值不值得说」——把语义判断塞进已有的第二段

第二段（`retellEvent`）本来就在读「刚做的事 + 你们的关系」，**顺带让它判断值不值得是免费的**：

```json
{"worth": true|false, "why": "一句话理由", "say": "值得时的那句话"}
```

- `worth=false` ⇒ **这次不打扰**（走已有的降级路径），日志记下理由
- **解析不出 JSON ⇒ 判不合格、不推**（宁可不说，也不瞎猜它想说什么）
- prompt 里给了判据，包括"**安静也是一种表达** —— 不值得就不要硬找话说"

## C. 表态时钟——第二根轴，只压额度

- 纯函数 `silenceCap(idleDays, quiet=3, mute=7)` 放在**事实层**（`context-facts.ts`）
- `life.ts` 推送门三处**取 min**：`min(配置, 档位 cap, 沉默 cap)`，沿用「只降不升」
- **不动亲密度衰减速率**（那会让"关系温度"也掉得飞快，是另一件事）
- 数值是**保守起点、不抄 whale**（它的 3/7 是在它自己的分享模型里调的）；可被 opts 覆盖；
  **每次真正生效都打日志**「silence cap 生效（idle=N天, …）⇒ 日上限 X → Y」，攒数据后再谈调整

## ★ 顺手抓到一个真 bug（被测试当场抓出）

第一版我写的是 `this.idleDaysSinceUserMessage()` —— 那是**显示包装**（`null → 999`），
于是「**从没说过话**」被当成「沉默 999 天」⇒ 沉默轴把推送**直接掐死**。
必须用如实的 `idleSinceLastUserMessage()`（`number | null`）。

这与两天前 `prove-intimacy-decay-reachable` 修的那个洞**是同一个形状**（哨兵值冒充缺失），
只是这次发生在额度侧。已加反向用例：`null` ⇒ **不受影响**。

## 测试

- `silence-clock.test.ts`（6 例）：null/0-2/3-6/≥7 边界、非法值、**可覆盖阈值**
- `life-service.test.ts` +6 例（接线）：沉默 0 / null → 不受影响；8 天 → 归零；
  4 天 + 已推 3 条 → 不推；4 天 + 已推 1 条 → 仍推；覆盖后第 8 天仍可推
- 顺带修 4 处 `retellEvent` 测试桩为 JSON；新增「worth=false 不推」「非 JSON 不推」两例
- 全量 **167 文件 / 1955 用例**

## 风险

- ⚠️ A 让第二段从纯文本变 JSON ⇒ 依赖 JSON 解析（已有 fence 容错；解析失败只是不推）
- ⚠️ C 会让"沉默多天"的她更快安静下来（3 天起）。数值可配，且有日志可观测。
