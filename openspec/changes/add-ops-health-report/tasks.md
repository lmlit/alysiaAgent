## 前置评估（提案明确要求的那一步）

**工具**：`scripts/log-profile.cjs <logfile> [topN]`（只读，全量统计，不采样丢行）
—— 把「噪声有多少、在哪」从印象变成**可重复的数字**。

**样本**：`packages/server/data/logs/alysia-2026-10-11.log`（本机唯一一份，1061 非空行）。
⚠️ **不是线上量级**（立项记录是 19,634 行），所以下面分「形态」与「量级」两栏读。

| 指标 | 本机样本 | 立项记录的线上 | 结论 |
|---|---|---|---|
| INFO 占比 | **97.8%** | 19,556 / 19,634 = 99.6% | 同形：INFO 压倒性 |
| WARN : ERROR | **9 : 14** | 16 : 11 | ⚠️ **不同**（本机 ERROR 反而更多） |
| 每 1000 行 WARN+ERROR | **21.7** | 1.4 | ⚠️ **量级差 15×** |
| 单一来源占比 | **`QQ Official` 84.0%** | `QQ Official` 96.6% | **同形**：单一来源压倒性 |
| 关心的信号占比 | `SessionEnd` **0.2%**（2 行） | 被 QQ 埋掉 | **这正是当初丢的那个信号** |

### 结论（三条，都可据上面数字复核）

1. **"噪声压死信号"的形态复现**：单一来源占 84~96.6%，而关键模块（`SessionEnd`）只占 **0.2%**
   ⇒ **按行数比例做监控必然无效**；必须按**模块/事件语义**而不是按日志行数取样。
2. **级别分布在本机样本里是「尚可用」的（21.7/1000），但线上不是（1.4/1000）**
   ⇒ 不能拿本地日志当设计依据；**上线前必须先在真实日志上跑一次 `log-profile.cjs`**。
3. ⚠️ **前置（日志系统整理）并未完成** —— 具体缺口：
   - **噪声抑制**：`QQ Official` 的逐条日志仍在（本仓已有 `warnThrottled` 这个手法，
     但只用在业务侧，**日志源头没做限频/分级**）；
   - **级别规范**：本机样本里 ERROR > WARN 且 8 行**没有 tag** ⇒ tag 不统一；
   - ⇒ 「日志系统建好其实监控很好做」这句**目前还不成立**。

## 实现方案（待用户重新拍板后再做，方向已定）

- [ ] **采集正确性指标**（不采存活指标 —— 存活指标骗过一次 22 天全绿）：
      摘要成功率 / 反思成功与重试数 / 各模块 WARN·ERROR 计数 /
      生活事件日条数 / QQ 重连次数
- [ ] **形态**：优先做 **B（阈值即时告警）**，例如「连续 3 次摘要失败」。
      ⚠️ 理由来自本仓自身的教训：**日报也会被埋**（22 天全绿的那次，指标是"活着"不是"做对"），
      而阈值告警在异常发生的当刻就发声，不依赖有人去看日报。
      （提案给的 A/B 二选一里，B 的信息密度更高、也更省人力。）
- [ ] **通道**：复用现有 proactive 推送，⚠️ **必须有 fallback**
      （QQ 官方 48h 互动窗口 ⇒ 长时间无互动时主动消息发不出）：
      退化顺序 = console 界面 → 日志（**但日志本身已证明会被埋，所以只能当最后兜底**）
- [ ] **不另起进程**：在现有 server 进程内聚合（本仓已有 `token_stats.json` 落盘先例）
- [ ] **先做前置**：QQ 日志源头分级/限频（否则告警自己也会被埋）
- [ ] 若新增只读端点（如 `/api/ops/health-report`）→ 必须先对照 `docs/Web-API-Design.md`
      （本仓有「doc 声明了 impl 没接」的先例：`add-platforms-endpoint`）
