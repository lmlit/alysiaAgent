# Change Proposal: improve-sticker-selection

## 元信息

- **日期**: 2026-10-16
- **类型**: NEW（素材选择策略 + 管理入口）
- **状态**: **pending（已立案，未动手）**
- **影响 spec**: `alysia-console` §7.2（大尺寸形象 = 表情包轮换）、`sticker-protocol`（frozen，可能需解冻）
- **来源**: 从 [`improve-sticker-system`](../../archive/2026-10-16-improve-sticker-system/proposal.md) 拆出。
  那个 change 的**首版只做了「渲染」**（计划明确收窄），其余三项在此立案。

## 为什么拆出来（而不是塞回首版）

修复计划对首版的原话是「**场景分组、选择权重、冷却和素材管理页后续再做，
不一次扩成完整素材平台**」。而这三项与「渲染」**没有代码耦合**：

- 渲染是**消费已有协议**（把标记变图片）—— 契约清晰、可单测、风险低；
- 这三项是**策略与运营**（怎么选、怎么管）—— 需要先定判据，且会改动
  `XilianFigure`、素材登记与世界书采样。

混在一起做会让首版的验证面从「一段解析逻辑」膨胀成「半个素材平台」。

## 要解决什么（三项，各自独立）

### ① hero 无差别随机 → 按场景分组

现状：`XilianFigure` 从全部 65 张里**均匀随机**抽，7 秒一张。
后果：会抽到「どうして?!」这类**情绪强烈**的图，放在"打招呼"的位置观感会跳一下
—— **素材有情绪，但场景没有**。

方向：给素材一个**场景维度**（hero 打招呼组 / 聊天共情组 / 其他），
`hero` 只从打招呼组抽。**判据要先定**：按文件名？按世界书条目字段？
按人工清单？（`sticker-protocol` 是 frozen，加字段要先决定要不要解冻。）

### ② 短时间重复 / 总是同一张 → 权重与冷却

现状：轮换已排除"与当前相同"的一张，但**没有跨时间的冷却**，
65 张里也可能连续两次抽到同一张（间隔一轮即可）。

方向：冷却窗口 + 权重（至少：**最近 N 张不重复**）。
⚠️ 要定"冷却记在哪"（内存 / localStorage）—— 跨页刷新是否要保留。

### ③ 65 张没有管理入口 → 素材管理页

现状：看不见有哪些、叫什么、哪些能用，只能翻文件系统。
方向：一个页面列出 `name` + 预览 + 启用/停用。
⚠️ **启用/停用要落在哪一层**：服务端 `data/stickers/` 是素材真相源，
前端禁用只影响当前浏览器（不可靠）—— 更可能是要服务端存一份开关。

## 动手前必须先定的事（**这是本 change 的第一项任务**）

1. 场景分组的**判据**（文件名 / 世界书字段 / 人工清单）—— 决定要不要动 frozen 的 `sticker-protocol`
2. 启用/停用的**落点**（服务端存储 vs 前端本地）—— 决定要不要加 API（进了 API 就要同步 `docs/Web-API-Design.md`）
3. 冷却的**作用域**（单页 / 跨页刷新 / 跨设备）

★ 三条没定之前不许写代码 —— 这正是首版拆出来的理由：
上一轮「素材换了、策略没换」的教训就是**范围与判据都没先定**。

## 明确不做

- 不改 `[表情包:名字]` 的**渲染**（已在首版落地，见 `alysia-console` §5.1.1）
- 不动素材本体（65 张二创图**不入公开仓库**）
- 不做完整素材 CMS（上传/裁剪/打标）—— 那是另一个量级

## 测试计划

待上面三条定了再写。届时预计：
- 选择策略抽成**纯函数**（当前 `XilianFigure` 里的 `pool` 逻辑），单测覆盖
  「冷却生效 / 组内只抽本组 / 只剩一张时不崩」
- 管理页若加 API，按 `docs/Web-API-Design.md` 走契约 + server 侧用例
