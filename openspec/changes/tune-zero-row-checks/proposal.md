## 这条要解决什么

`docs/KNOWN-ISSUES.md` **KI-11**：全 core 55 个写入点里只有 3 处检查 `.run().changes`。
`UPDATE … WHERE id = ?` 命中 0 行**不报错** —— 「改到了」和「什么都没改」完全同形，
这是本项目栽过三次的「**空转伪装成归档**」的产地。

已知受害点：
- `LifeStore.markDelivered` —— "已推送"这一位不可信（反向会导致**重复推送**）
- `WorldbookStore.recordTrigger` —— 命中计数空转 → **世界书采样权重失真**
- `WorldbookStore.updateEntry` —— 编辑不存在的条目**返回成功**
- `PersonaStore` 的 8 个 `WHERE is_active = 1` 写方法 —— 没有激活行时
  「**读到正常人格 + 写入 0 行 + 不报错**」三件事同时成立并报成功
- `EventStore.archiveBySession` / `deleteBySession` —— **祖先级**「空转伪装成归档」
- `ConversationStore.updateSummaryResult` —— 0 行更新仍打「补处理成功」

## 为什么**现在不**做（这条为什么是 pending）

`changes === 0` 有**两种含义，且静态分不出来**：

| 含义 | 例子 | 该不该报错 |
|---|---|---|
| **正常**：幂等跳过 | `INSERT OR IGNORE` 遇到已存在的行 | ❌ 不该（会变成每次启动的噪声） |
| **异常**：目标行不存在 | 写错 id / 行被并发删除 / **表结构不对（列没迁上）** | ✅ 该 |

一刀切硬校验会把正常路径变成噪声，**比现在更糟**。
**先取证据，再改代码**（HANDOFF 约定 6；KI-1 就是这么处理的）。

## 怎么做（等数据到位后）

1. **采集**（已由 `observe-zero-row-writes` 完成）：写点命中 0 行时打
   `[WriteTrace] <类名.方法名> 命中 0 行 — <上下文>`
2. **统计**（**待用户执行/下次会话**）：从线上日志按 tag 聚合：

   ```bash
   grep -o '\[WriteTrace\] [^ ]*' alysia-*.log | sort | uniq -c | sort -rn
   ```

   得到每个写点的「0 行发生率」与触发场景。
3. **定性**：对每个 tag 判断属于上表哪一类 ——
   - 高频率 + 幂等语义 → **豁免**（并在代码注释写明"0 行是设计意图"）
   - 任何频率 + 语义上"必须有目标行" → **升级为硬校验**（`changes === 0` 时
     `logger.error` + 返回失败，让调用方能判）
   - 零触发 → 暂不动，保留观测
4. **落地**：按定性结果改代码 + 把「逐点口径表」写进 `memory-system` §4.7；
   然后本 change 才能 apply → archive。

## ⚠️ 采集期要注意的

- **`[WriteTrace]` 是观测噪声，不是故障** —— 别拿它当告警。它的职责是分布采样。
- **别只看总量**：要按 tag 分开统计，否则"某一个点狂刷"会淹没"另一个点偶尔真丢"。
- **表结构不对（列没迁上）也会表现为 0 行** —— 若某个 tag 是"全线 0 行"，
  先查 `database.ts` 那次迁移是否真的成功了（§4.7 契约 1 已把迁移改成失败即抛）。
