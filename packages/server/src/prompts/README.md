# 提示词资产目录

送进 LLM 的 systemPrompt 集中在这里，与模块装配代码分开。

| 文件 | 用途 |
|---|---|
| `life.ts` | `al:life` 的 5 段：事件生成 / 每日摘要 / 承诺裁决 / 情绪侧端 / 每日反思 |

## 为什么不是 `.md` 资源文件

计划里本来要外置成 `.md` + loader（照 `packages/core/src/persona/` 的做法）。
动手前核对发现**两个方案都要付代价，而收益在这个项目里站不住**，故改为 TS 常量。

**① 「逐字不变」与「可读」不可兼得**

多行提示词在原码里是**无分隔符拼接**：

```ts
'……决定怎么做：' +
'① fulfill=兑现：……' +
```

运行时是 `：①`。放进 `.md` 会变成两行 → 运行时 `：\n①` —— **这是内容变更**。
要么 `.md` 里是一行 2000+ 字的巨型文本（比原码还难读），要么接受提示词多出换行。

**② 收益没有对应的工作流**

外置的卖点是「用文本编辑器改提示词，不用碰代码」。但本项目**改完仍要重新构建 + 部署
Docker 容器**（见 `docs/Docker-Deployment.md`），不存在热改场景。
省下的只有「打开 .ts 而不是 .md」这一点点。

**③ 新增两类故障面**

- 构建要加 `cpSync` 把资源拷进 `dist/`（core 的 persona 就是这么做的）
- 运行时要做路径解析——**正是 `docs/dsh-migration-guide.md` 坑 #2 的同类坑**：
  路径算错 → `existsSync` false → **静默不生效且无报错**

## 什么时候该回头做

出现下列任一情况，再考虑 `.md` + loader：

- 提示词要在**不重新构建**的前提下调整（例如接进管理面板热改）
- 需要让**非开发者**编辑提示词
- 提示词数量增长到十几段，单文件难以导航

## 搬运纪律

从模块里搬出时用脚本做**文本切片**（不是手抄），并在脚本里断言搬运前后**逐字符一致**。
新增提示词时沿用同样做法——提示词内容变了是**行为变更**，必须能证明没变。
