> 不能直接照此文件实施；本文件不构成已批准的 change。

**版本：2026-10-16**

**当前状态：仅制定计划，不修改代码、不部署、不调用服务器。**

> 核心原则：**先修记忆链路，再让聊天侧 Alysia 委托 dsh 中的 Alysia 模式完成博客任务，最后把成果带回聊天。**

> 不重建编程框架，不复制一套人格，不把两个执行环境的全部消息互相转发。

## 一、执行模型必须遵守的规则

以下规则应放在实施任务的开头，不能只放在背景文档里。

| 编号 | 规则 |
|---|---|
| R01 | **禁止在本地修改代码。** 只能在用户指定的服务器开发工作区实施，不等于直接修改运行中的服务目录。 |
| R02 | 开始前确认服务器、工作目录、分支、当前提交和未提交修改。任一信息不明确，停止并询问。 |
| R03 | 不覆盖、不清理、不提交他人的修改；发现与任务重叠的已有修改，先询问。 |
| R04 | 不向外传输聊天、画像、数据库、日志正文、密钥或服务器配置；测试使用虚构数据。 |
| R05 | 不猜 dsh API、CLI 参数、preset ID、事件类型或响应结构。每个接口必须有源码、帮助信息或实际输出依据。 |
| R06 | 不因为文档写“已归档”就认定已部署；分别记录代码、测试、部署和验收状态。 |
| R07 | 遵守仓库 OpenSpec 流程。复用已有问题编号和 change，不重复立项。 |
| R08 | 一次只实施一个任务卡。完成验收后，再进入下一项；不能顺手重构无关模块。 |
| R09 | 不改模型配置。实际工作模型使用用户指定的 `deepseek-v4.1-flash`；若服务端标识不同，先核实映射。 |
| R10 | 未执行的测试必须写“未执行”；模拟测试不能写成真实 dsh 联调通过。 |
| R11 | 不自行修改系统服务、反向代理、防火墙、域名、凭据或其他项目。需要时单独申请。 |
| R12 | 第一场实验禁止自动发布博客、定时执行和任意 shell 委托。 |

**不确定时的处理：记录缺口并停止该任务，而不是构造一个“看起来能用”的接口。**

## 二、最终要打通的流程

```text
用户与聊天侧 Alysia 讨论博客
              │
              ▼
Alysia 生成工程任务
项目、目标、限制、验收标准
              │
              ▼
Alysia 服务保存任务并提交给 dsh
              │
              ▼
dsh 使用已核实的 Alysia 模式
在博客专属工作区内执行
              │
              ▼
返回任务状态、修改摘要、检查结果、预览
              │
              ▼
聊天侧 Alysia 查看结果
满意 → 交付用户
不满意 → 在同一个 dsh 工程会话继续修改
```

### 四个职责边界

| 部分 | 负责什么 | 不负责什么 |
|---|---|---|
| 聊天侧 Alysia | 提出目标、选择风格、验收、提出修改 | 不直接代替 dsh 执行工程命令 |
| Alysia 任务协调层 | 任务持久化、身份映射、提交、状态同步、结果去重 | 不再实现一套 Agent 推理循环 |
| dsh Alysia 模式 | 使用工程工具完成任务，保留工程会话上下文 | 不修改 Alysia 的用户画像，不操作其他服务器项目 |
| 博客项目 | 源码、内容、构建和预览产物 | 不保存聊天系统凭据或私人记忆库 |

**“同一个她”通过共享人格与项目背景实现，不通过共享全部会话、数据库写权限或系统提示实现。**

## 三、范围划分

### 本期必须完成

- 记忆回传的基础缺陷修复。
- 核实服务器 dsh 的真实调用方式。
- 固定博客项目映射。
- 提交任务、查询状态、接收结果。
- 恢复任务与避免重复提交的基本机制。
- 继续同一个工程会话。
- 明确区分用户指令与 Alysia 自主委托。
- 完成“关于我页面 → 预览 → 一次修改”的实验。

### 本期明确不做

- 自主发布公网博客。
- 定时写日记、定时维护。
- 任意项目路径、任意 preset、任意服务器命令。
- 并行多工程任务、复杂任务调度平台。
- 全面统一人格和记忆系统。
- 自动清理历史污染数据。
- 召回参数调优、模型切换。
- 恢复 Live2D、增加语音或绘图。

## 五、阶段 B：修复基础问题

这部分沿用已有修复计划，不与博客功能混成一个大提交。

| ID | 任务 | 关联问题 | 实现要求 | 必须通过的测试 |
|---|---|---|---|---|
| B01 | 会话身份校验 | KI-23 | ID 无效时不回传、不刷新、不结算；不能混入 `unknown` | 两个缺失 ID 的会话不会混桶 |
| B02 | 事件幂等 | KI-12 | 重传不覆盖归档、处理位、重要度；不重复学习；同 ID 不同内容明确拒收 | 同事件重复提交、归档后重投、内容冲突 |
| B03 | 分批回传 | 单批上限问题 | 每批不超过服务端限制；失败保留待发事件 | 201/500 条积压可排空 |
| B04 | 在途串行化与结算 | KI-24 | 等该会话消息确认落库后再结算；失败不抢跑 | 回传过程中关闭会话、断连重试、多会话交错 |
| B05 | 合成消息来源核对 | KI-20 | 找到可靠来源依据；不凭一句文本前缀全面过滤 | 合成上下文不学习，真实用户引用不误删 |
| B06 | 已有反思修复状态 | 已实现修复 | 核实运行版本是否包含修复，不重写、不默认重跑迁移 | 新生成的测试反思进入角色事实 |
| B07 | 检查迟到事件窗口 | KI-19/24 相关 | 验证 cron 是否能越过在途消息推进窗口；若成立，独立修复 | 延迟入库事件不会被永久排除于应处理窗口 |

### 执行注意事项

- **B02 不要求立即更换 `event.seq`。** KI-25 的上游身份语义先核实。
- B04 不能只证明“调用顺序正确”，还要证明**结算前落库已经确认**。
- B05 尚无可靠来源依据时，保留阻塞，不编造识别规则。
- 所有测试用虚构消息，不重放真实用户历史。
- 若自带高权限文件工具会被本实验使用，路径边界修复必须提前完成；否则本实验不启用该执行路径。

### G1：进入打通实施的条件

- B01—B04 已验证。
- 新的工程委托不会被误记为用户发言。
- B07 有明确验证结论；发现的实际缺陷不能靠“以后观察”绕过。
- 仍未解决的旧污染问题已被隔离出实验路径。

## 六、阶段 C：确定最小任务契约

**下列名称是 Alysia 内部的拟议能力，不代表 dsh 已有同名 API。**

### 1. 给聊天侧开放的能力

| 拟议能力 | 输入 | 输出 | 限制 |
|---|---|---|---|
| `start_project_task` | 项目 ID、目标、验收标准 | Alysia 任务 ID、初始状态 | 项目必须已登记；不接受任意路径 |
| `get_project_task` | 任务 ID | 状态、摘要、检查结果、产物引用 | 只返回该任务允许读取的信息 |
| `continue_project_task` | 任务 ID、具体修改意见 | 新一轮任务状态 | 继续同一工程会话；运行中不能重复发起 |

首版模型可调用工具**不包含发布工具**。取消能力根据 A05 核实结果决定，不能把“本地不再等待”伪装成“远端已经停止”。

### 2. 固定项目映射

首版只登记一个博客项目：

| 字段 | 决策 |
|---|---|
| 项目 ID | 固定逻辑标识，例如 `alysia-blog` |
| 工作目录 | 由用户指定，服务端配置，不由模型填写 |
| dsh 模式 | 使用 A03 核实出的真实 Alysia preset |
| 执行权限 | 仅博客项目必需的权限 |
| 发布权限 | 首版关闭 |
| 同时运行数 | 同一博客最多一个在途任务 |
| 模型 | 沿用用户现有工作模型，不擅自切换 |
| 预算 | 配置单任务时限与执行上限，具体数值实施前确认 |

### 3. 最小任务记录

| 字段 | 用途 |
|---|---|
| `taskId` | Alysia 侧稳定任务 ID |
| `requestKey` | 同一次工具调用重试去重，不使用正文哈希代替 |
| `projectId` | 固定项目身份 |
| `originSessionId` | 最初发起任务的聊天会话 |
| `origin` | 用户授权执行，或 Alysia 在预授权范围内自主发起 |
| `goal` / `acceptanceCriteria` | 目标与验收标准 |
| `dshSessionId` | 经真实响应确认的工程会话 ID |
| `status` / `revision` | 当前状态与任务轮次 |
| `result` / `artifacts` | 结果摘要、检查结果、受限产物引用 |
| `createdAt` / `updatedAt` | 审计与恢复依据 |

建议复用现有 SQLite 持久化，不引入外部队列服务。

### 4. 状态定义

```text
queued → submitting → running → needs_review → completed
                 │        │
                 │        ├→ failed
                 │        └→ unknown
                 └→ unknown

needs_review → 用户或 Alysia 提出修改 → 新 revision → queued
```

- `needs_review`：dsh 已结束本轮，但尚未完成产品验收。
- `completed`：本轮结果被接受，不等于已经发布。
- `unknown`：无法确认远端是否执行成功，**不能自动重新提交**。
- `failed`：有明确失败证据，不是单纯网络请求超时。

## 七、阶段 D：实现任务与结果通道

| ID | 任务 | 实现边界 | 验收标准 |
|---|---|---|---|
| D01 | 项目登记与校验 | 只允许博客项目；路径、模式由配置映射 | 任意路径和未知项目被拒绝 |
| D02 | 任务持久化 | 提交前保存任务与去重键 | 重启后任务仍可查询 |
| D03 | dsh 调用适配层 | 仅封装 A05 确认的接口 | 使用模拟执行器通过提交、失败和恢复测试 |
| D04 | 异步任务提交 | 聊天工具尽快返回任务 ID，不等待整个编码完成 | 长任务不阻塞聊天 |
| D05 | 状态同步 | 有限频率查询或真实事件订阅；终态停止跟踪 | 不无限轮询、不重复消费结果 |
| D06 | 结果收集 | 保存摘要、测试结果、预览引用；限制长度与路径 | 不读取任意文件，不暴露凭据 |
| D07 | 回到原聊天 | 结果按任务 ID 回送一次；失败时仍可主动查询 | 不发到错误会话，不重复通知 |
| D08 | 继续工程会话 | 使用保存的 `dshSessionId`，增加任务 revision | 第二轮修改延续首轮成果 |
| D09 | 工具注册 | 按现有模块和工具注册方式接入，提供能力开关 | 未配置或关闭时不暴露工具 |
| D10 | 记忆来源隔离 | 工程委托、工具输出和结果分别标记 | 不作为用户事实直接进入画像 |

### 不能省略的失败处理

| 场景 | 必须行为 |
|---|---|
| 提交前网络失败，确认未发送 | 可按明确策略重试 |
| 提交请求超时，不确定远端是否已接受 | 标为 `unknown`，先查询或核对，禁止直接再创建 |
| dsh 已完成，Alysia 尚未拿到结果 | 恢复后重新查询同一任务，不重新编码 |
| Alysia 服务重启 | 恢复未完成记录，不默认再次提交 |
| 博客已有任务运行 | 返回已有任务或明确忙碌，不启动第二个并发修改 |
| dsh 会话失效 | 明确报告；不能静默新建会话并假装连续 |
| 结果通知失败 | 任务结果仍可查询；通知重试必须去重 |
| 远端取消能力不可用 | 明确显示无法确认停止，不能把任务标成已取消 |

## 八、人格与记忆的具体规则

这里是最容易“看似接通、实际污染”的部分。

### 可以共享

- 已有的人格配置和明确表达偏好。
- 博客项目目标、设计决定和当前进度。
- 用户授权公开的素材。
- 本次任务需要的少量背景。

### 不默认共享

- 全部私人聊天。
- 用户画像全文。
- 服务器部署凭据。
- 其他项目的代码或内部资料。
- 完整历史工具日志。

### 必须避免的循环

```text
Alysia 自动委托
   → 被 dsh 当成 user/message 回传
   → 被画像提取器当成用户真实表达
   → 形成新的“用户偏好”
```

**解决要求：**

1. 自动委托会话必须有可验证的来源标记。
2. 不能只通过“换一段提示词”解决来源问题。
3. 来源标记在提交、回传、结算过程中不能丢失。
4. 如果 dsh 不支持所需标记，首版对实验工程会话关闭原始消息学习，改为仅导入经过类型化的项目结果。
5. 不能通过全局关闭正常 dsh 会话的记忆回传来掩盖问题。

## 九、阶段 E：博客实验任务表

### E01：无副作用连通测试

**任务内容：** 让 dsh 返回当前任务身份、选中的模式和指定工作目录的确认信息，不修改文件。

**通过条件：**

- 确认使用真实 Alysia 模式。
- 确认任务对应正确工作区。
- 聊天侧能看到结果。
- 没有触发公开发布或私人记忆写入。

### E02：创建“关于我”页面

给 Alysia 的任务只规定边界，不替她做审美决定：

> 为自己的个人博客设计一个“关于我”页面。你可以决定名称、风格、文字与布局。页面应自然说明 AI 角色身份，不捏造现实身份或真实经历。不使用私人聊天、服务器信息或未经授权的素材。只生成本地项目和预览，不发布。

**通过条件：**

- 她提出可理解的设计决定。
- dsh 产出真实文件。
- 构建结果来自实际命令，不是模型自述。
- 预览可以被用户或具备视觉能力的验收路径查看。

### E03：查看预览并提出一次修改

- 如果聊天侧具备实际图像检查能力，让她查看截图并给出具体意见。
- 如果不具备，不得声称“看过页面”；由用户反馈，或先接入经核实的视觉验收路径。
- 第二轮必须继续同一个工程会话，而非重新建站。

**通过条件：** 有明确的“首轮结果 → 修改意见 → 第二轮产物”证据链。

### E04：恢复测试

在合成任务上模拟查询中断或 Alysia 重启。

**通过条件：** 任务可恢复查询，不重复建站、不重复通知、不把未知状态当完成。

### E05：实验总结

只回答：

- 是否真正调用了 dsh 的 Alysia 模式。
- 是否共享了正确的人格与项目背景。
- 是否完成一次多轮工程修改。
- 是否出现记忆污染。
- 哪些步骤仍需人工参与。
- 哪些能力尚未接通。

**E05 通过，才讨论完整博客、自主写作和自动发布。**

## 十、统一测试清单

执行模型不能只写“测试通过”，必须逐项报告。

| 测试 | 预期 |
|---|---|
| 同一次提交重试 | 只产生一个逻辑任务 |
| 提交响应丢失 | 不盲目创建第二个远端任务 |
| 同博客并发请求 | 不发生两个任务同时改工作区 |
| 未知项目 ID | 被拒绝 |
| 任意工作目录输入 | 不被模型直接控制 |
| 未核实 preset ID | 不提交 |
| dsh 不可达 | 聊天仍可用，任务状态明确 |
| 状态查询失败 | 不误报任务失败或成功 |
| 重复完成事件 | 只记录、通知一次 |
| 工程结果包含敏感字符串 | 不原样回显或发布 |
| 自动委托消息回传 | 不形成用户画像事实 |
| 继续任务 | 使用原工程会话及新 revision |
| 服务重启 | 恢复状态，不重复执行 |
| 构建失败 | 不进入“验收通过”状态 |
| 没有截图或预览 | 不声称已进行视觉验收 |
| 首场实验结束 | 不自动发布、不自动启动下一项任务 |

## 十二、实际实施顺序

```text
A：确认服务器环境与真实 dsh 接口
        ↓ G0
B：修复基础回传、幂等、结算与来源问题
        ↓ G1
C：确定内部任务契约与权限边界
        ↓
D：实现任务提交、结果返回、同会话续作
        ↓ 模拟测试通过
E01：只读连通测试
        ↓
E02—E03：“关于我”页面 + 一次修改
        ↓
E04—E05：恢复测试与实验验收
        ↓
另行制定完整博客和自主维护计划
```

**最重要的验收不是“她调用了一个工具”，而是：聊天中的她能够把想法交给 dsh 的 Alysia 模式执行，得到真实成果，继续提出修改，并且整个过程没有丢任务、污染记忆或越过权限边界。**
