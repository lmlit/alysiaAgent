# 静默失败族（根因审计）

> 建立于 2026-10-18。**这份文档回答"为什么这几条 KI 是同一个病"，不替它们做修复登记。**
> 在办清单见 [TODO.md](TODO.md)；正文与证据见 [KNOWN-ISSUES.md](KNOWN-ISSUES.md) 各自小节。
>
> 存在理由：KI-4/5/11/13/14/15/21/25/26 分散在一份 64KB 的登记册里，
> 读起来像 **九个小毛病**；实际上它们是**一个缺陷的九种形态**，
> 分开修必然修一半、留一半，而且修完的还会复发。

## 1. 一句话结论

本项目的线上事故**从来不是"代码算错了"**，而是"**出错了但没人知道**"。
截至 2026-10-18，这个族里 **14 条已修、6 条还开着**；
剩下 6 条的共同特征是：**修它们不需要新功能，只需要让失败有出口。**

## 2. 什么叫"静默失败"

失败没有变成**异常**、**日志**或**非零计数**，而是变成了一个看起来正常的返回值。
具体只有三种形态：

| 形态 | 机制 | 判据（怎么算复发） |
|---|---|---|
| **吞** | `catch {}` / 错误压成空串 / `?? ''` | 出错路径与正常路径**返回值相同** |
| **空转** | `UPDATE … WHERE` 命中 0 行不报错 | 「改到了」与「什么都没改」**同形** |
| **缺** | 参数没声明 ⇒ 被静默丢弃；分支没实现 ⇒ 静默跳过 | 调用方以为生效了，实际没生效 |

三种形态的共同点：**错误被降级为"没有发生"**，于是所有下游判断都建立在假数据上。

## 3. 为什么是一个族（不是九个 bug）

三条线上事故，三份不同的代码，**同一条根因**：

| 事故 | 形态 | 后果 |
|---|---|---|
| 会话摘要失败 | 吞（空响应） | **22 天 100% 失败**，期间 healthcheck 全绿 |
| 每日反思空响应 | 吞 | 11 次空转，无人察觉 |
| 画像提取静默停摆 | 吞 + 缺 | **6 个月**没有新 facts |

它们的共同后果不是"功能坏了"，而是"**她安静地变成了半个她**" ——
坏了但行为仍然合理，所以永远不会被当成 bug 报告。

这就是为什么这条族的优先级**不因"个人产品"而降级**：
团队里别人会撞上并告诉你，个人产品只有一个线上实例，而它不会说话。

### 4.3 新入族：**不可达**（2026-10-24，第四种形态）

前三种形态是「吞 / 缺 / 空转」——都在**执行**上失败。这一条不一样：**代码执行正常、日志正常、测试全绿，但条件永远为假**。

**案例：亲密度「无互动衰减」永不触发**（`packages/server/src/life.ts` 的 `updateIntimacy()`）。

| 时点 | 代码 | 可达性 |
|---|---|---|
| `7f08f73` LifeService 初版 | 窗口 `since7d` = **7 天**；条件 `if (idleDays >= 3)` | ✅ 可达 |
| **`07c9016`（08-07）** `wire memory_config knobs into intimacy calc` | 修的是"旋钮从未参与决策"（硬编码 → 配置驱动）：<br>`decayThreshold = 2 + round((1-0.4)×10)` = **8** | ❌ **不可达** |

窗口没动过 ⇒ `idleDays` 的**可观测上限就是 7**（且兜底写死 `: 7`），而阈值是 **8**。
**那次修复做对了它想做的事，顺手把门槛抬过了数据窗口的天花板。**
更细：即使把阈值降到 7，衰减幅度 = `1.8 × (7−7+1)` = 1.8 —— **只衰减一天量就封顶**，窗口不解决，阈值调多低都只衰减一次。

**为什么 2 个月没人发现**

`life-service.test.ts:398` 那条用例的标题就是
「5 天无 user 互动 → **未过 8 天阈值，不衰减**」——
它守的是「不该触发时**不**触发」。**这一侧永远是绿的，因为根本触发不了。**
没有任何一条用例构造过 ≥8 天的 idle。

**入族判据（可机器化，写进 change 的验收）**

> 任何 `if (x >= T)` / `if (x < T)` 形式的阈值判据，**必须**有一条用例把 `x` 构造成**跨过 T 的两侧**。
> 只测"没跨过"等于没测 —— 它连"函数被调用过"都证明不了。

**同族第二例（同一天发现，形态是「死参数」）**

`PromptAssembler.assembleChat` 的 `triggers` 参数：收下了、`recordTrigger()` 计数了、日志打着
「worldbook N 条」，**函数体一次未引用** ⇒ chat/dsh 侧的世界书从未进过 prompt（读通道 10-02 上线 → 10-24 发现，22 天）。
判据同款：**"参数被接收"不等于"参数被使用"**，需要有断言证明它的效果出现在输出里。

**两者的共同点**：**都没有任何一行错误日志**。这也是它们只能靠"主动去算一遍可达边界"才发现的原因 ——
不属于"看日志找异常"能解决的类别。

## 5. 修复顺序（为什么是这个顺序）

```
① 让错误有出口      KI-5（4 处裸 catch）           ← 成本最低，也是②③的观测前提
② 让缺口可见        KI-26（摘要遗漏）、KI-25（取证） ← 不改行为，只加 warn + 计数
③ 让判断生效        KI-11、KI-1、KI-2               ← 需要数据，已在各自 change 里等
```

**顺序不能倒。** ②③ 的决策全部依赖 ① 的存在：如果裸 catch 还会吞掉异常，
那么"加了观测"也只是多一个不响的日志。

## 6. 验收标准（可机器判定，不靠感觉）

1. **`catch {}` 全仓为 0** —— `grep` 可验，可接进 `scripts/check-*.cjs` 与 pre-commit。
2. **每个"静默跳过"点都有一行带固定 tag 的 warn** —— 可被日志聚合，而不是散文式描述。
3. **30 天后能用数据回答**：`finish=length` 占比、`[WriteTrace]` 分布、摘要成功率。
   —— 答不出来 = ②③ 没做到位。
